# 本项目的架构决策与踩坑记录

每条都按「症状 → 根因 → 结论」写。改动核心逻辑前请先扫一遍。

## 一、规则回放器必须和 Legado 语义一致

**症状**：脚本验证通过的源，导入 App 后不能用；反之 App 能用的源被判失败。

**根因**：早期的 `apply_css_rule` 只做

    selector, _, attr = rule.rpartition("@")   # 取最后一个 @
    soup.select(selector)                      # 然后 el.get(attr)

它**不支持 Legado 的 `class.` / `tag.` 前缀简写、`##正则##替换`、`@js:`、JSONPath**。
一条 `tag.a@text##作者：##` 的规则会被当成属性名 `text##作者：##`，取到空字符串——
于是「内容为空」被误判成「规则失效」。

**结论**：验证器和执行引擎必须是同一套语义。规则解析统一走
`core/rules/replayer.py`，且**不支持的语法要返回明确原因**，
由调用方判为「无法验证」而不是「失效」。误杀比漏放更贵。

## 二、静默失败是最贵的 bug

**症状**：`--probe-depth 2/3` 跑完（2026-09-16 起改为四档，那是当时的编号，即现在的
3/4），`toc_complete` / `content_ok` 全是 `None`，深度验证看起来「没查出来」，
实际**一个额外请求都没发**。

**根因**：`requirements.txt` 里漏了 `beautifulsoup4`。
`apply_css_rule` 里 `from bs4 import BeautifulSoup` 写在 `try` 之外，
一调用就抛 `ModuleNotFoundError`；上层 `except Exception` 把它吞了，
统一变成「无法验证」。连带 `_confirm_hit` 的异常分支返回 `True`，
命中判定退化成「响应体里出现关键词就算命中」。

**结论**：所有「无法验证」的返回路径都要能说出原因，并且要有
`err` / `fail_reason` 字段一路透传到报告。**异常吞掉之后必须留下痕迹。**

## 三、失效必须分桶，不能只有一个 DEAD

**症状**：报告里 `❌失效` 一大堆，人没法判断哪些该删、哪些该修。

**根因**：`checker` 只判「域名通不通 + 搜索有没有命中测试词」。
三种完全不同的情况挤在一个桶里：

- 域名注销的死站（该删）
- 域名活着但页面改版、规则过期的源（**可修，不该删**）
- 域名活着但已转型的站点（该改类型）

**结论**：拆成四类归因——`死站` / `规则漂移` / `站点转型` / `需验证`。
判据是「域名可达性 × 反爬特征 × 搜索页能否解析 × 实测类型」的组合。
`diagnose` 命令就是这个设计的实现。

## 四、类型必须实测，不能信声明值

**症状**：明明是漫画站，被标成小说源。

**根因**：`add` 命令的类型来自 `--type`（默认 `novel`），
`bookSourceType` 从未被实测校验过。默认值一路写进库。

**结论**：`reclassify` 用「静态信号 + 首页/正文实测」反推类型：
域名/名称关键词、是否有 `ruleContent.image`、正文规则取的是图片还是文本、
`imageStyle=FULL`。累计打分 ≥3 且高于另一方向才改判，否则保持原样。
**实测优先于声明。**

## 五、URL 必须规范化后再作为 key

**症状**：迁移后 `v_sources` 里 571 个源查不到校验记录，
健康度分布比报告少 571 条。

**根因**：`upsert_sources` 存的是 `_normalize_url(bookSourceUrl)`，
而 `save_checks` 存的是缓存里的原始 `url`。两者不是同一个字符串，
SQL JOIN 自然对不上。

**结论**：**任何跨表/跨库关联的 URL，两侧都必须用同一套规范化函数**
（`core/loader._normalize_url`）。这类 bug 不会报错，只会静默丢数据——
所以**迁移必须做一致性校验**（源数/类型/健康/星级四项分布对比），
不做这步它就一直藏在库里。

## 六、缓存去重键也要规范化

**症状**：两个缓存目录合计 10166 条，归一后只剩 5591 条。

**根因**：同一站点存在多个 URL 变体（带不带尾斜杠、http/https、
带不带 `#` 锚点），`load_cache` 按原始 url 去重，等于没去。

**结论**：去重和查询都用规范化 URL。合并掉 4575 条重复后，
`cache_parity` 的命中矩阵才从「185 单侧差异」变成「200/200 完全对齐」。

## 七、SQLite 而不是 MySQL

**理由**：单用户本地工具。Python 标准库自带、零运维、单文件、
`VACUUM INTO` 就能备份。3734 源 + 5591 校验 ≈ 25MB，
离 PostgreSQL/MySQL 的合理起步量级差几个数量级。

**必须配的 PRAGMA**：

    journal_mode=WAL          # 读写并发（Job 写的同时前端能查）
    synchronous=NORMAL
    foreign_keys=ON
    busy_timeout=5000         # 避免 backend/job 撞车直接 database is locked
    temp_store=MEMORY

**关键约束**：**DB 文件不能放网络盘（SMB/NFS）**。SQLite 依赖文件锁，
在网络挂载上会静默损坏。若服务跑在 NAS 上，DB 放 NAS 本地卷，
备份产物才放网络盘。

**什么时候才该换**：① 多机多人同时写；② `busy_timeout` 频繁超时；
③ 单库到几十 GB。单机单用户不会碰到。

## 八、状态归一：别让三个 store 靠代码 merge

**症状**：一个源的信息散在 `candidates.json`（规则/分组/类型）、
`check_cache/*.ndjson`（健康/星级）、`book_sources.sqlite3`（审批），
`organizer.py` 存在的意义就是把这几个拼起来。

**结论**：一行一个源放进 `sources` 表，校验结果进 `checks` 表，
`v_sources` 视图直接 LEFT JOIN 最近一次。merge 逻辑消失。

## 九、AI 只提议，验收必须由回放器做

**结论**：`repair` 的闭环是

    抓证据 → 模型提议 → legado_rules 回放验证 → 失败差异回喂 → 重试

让模型直接输出书源、然后相信它，和早期的启发式推断一样不可靠。
**验证证据要压缩**：把几 MB 的 HTML 压成 90 行缩进 DOM 大纲，
模型只做「修正」而不是「从零发明」选择器。

## 十、搬迁与重构的教训

**症状 → 根因 → 结论**：

- **反向依赖**：`checker.py`（核心）为了一个 `_abs_url` 依赖了 57KB 的
  `add_source.py`。→ 抽出 `core/urls.py`。**核心层不应依赖 CLI 工具。**
- **`from __future__` 位置**：往 `cli/main.py` 头部插 `sys.path` 引导，
  直接把 `from __future__ import annotations` 挤到非法位置。→
  插代码前先检查文件头。
- **venv 可以搬**：Windows 上 `.venv` 移动后仍可用（`pyvenv.cfg` 里的
  home 是绝对路径，没变）。但**别在搬迁脚本里做**，单独一步、单独验证。
- **`tests/` 目录只读**：沙箱限制。搬迁时用「读源 + 写到新位置 +
  `git rm --cached`」，不要用 move。

## 十一、验证手段的优先级

1. **单元测试**（离线、可注入假依赖）——`repair` 循环有 8 项离线测试，
   注入假 LLM 与假验证器，不联网就能验完整闭环
2. **import 冒烟**——每次改完立刻 `python -c "import 模块"`
3. **一致性校验**——迁移后四项分布对比
4. **双跑对比**——切换后端后 `cache_parity` 验等价
5. **真实联网跑小样本**——最后才做，且比分布不比逐条（网络有抖动）

## 十二、变异测试会把中间态提交进去

**症状**：HEAD 上出现一个自相矛盾的提交——`PAGE_IDS["explore"]` 被写成 `"detail"`，
而**同一个提交里**的测试断言它必须是 `"explore"`。HEAD 全量 3 failures，工作区却是绿的。

**根因**：本项目的测试惯例是对新增用例做**变异测试**——临时把源码某一行改坏、跑全量
确认预期条数变红、再改回来，结果记进测试文件底部的变异表。变异态只存活几秒到十几秒，
而 **`git add` 抓的是磁盘当时的内容**，不是你以为的状态；那次提交恰好落在「改坏」的窗口里。
坑还不止于单人操作：本仓库出现过子任务与主会话同时改同一批文件、而且在做同一件事。

**结论**：做变异前先把当前状态提交成 WIP，或用 `git worktree` 隔离出干净副本再变异；
**变异窗口内绝不 `git add`**。多会话/子任务并行时，提交前先确认没有别的 writer 落在
同一批文件上。

**变异没变红时，先分清是哪种情况**：要么用例太弱，要么这是个**等价变异**（两条分支
在该输入下本就同判）。别默认前者、更别默认后者——去打印两边实际的返回值再定。
实例：把 `replay_step` 的列表分支改成一律走 `judge_content`，用例全绿；查下来是
下载源上两个 judge 都返回 unknown、短文本都判 pass。**只断言 `verdict` 的用例守不住
分支走错**，补一条断言 `reason` 的才红。

变异测试本身也别用「改完再改回来」的脚本 `write_text` 落地——见
`agent-write-safety` 里那条行尾陷阱。

**跑变异要带 `python -B`**：等长替换（`3`→`1`、`>= 5`→`>= 4`）不改变文件尺寸，
字节码缓存可能不失效，于是测试跑的是**上一轮变异**的编译产物。症状很坑——
报出来的确实是"✔ 变红了"，只是失败用例的名字和这个变异对不上（实测三条不同变异
报了同一个用例名）。看着通过、实则没测到，比不跑更危险。写变异脚本时顺手记下
每条变异**应该**让哪个用例变红，名字对不上就说明测量本身出了问题。

### 补充：本轮（2026-09-16）实测的两条

**变异要能复现「改动前」，多处改动只还原一处等于没测。**
`@html:` 前缀那处改动散在**三个地方**（`RULE_PREFIXES` 的映射、`parse_rule` 里的
早退、`_root_of` 的分支）。造变异时只把映射加回去，**测试全绿**——因为另外两处已删，
`steps` 是空的，行为根本没还原。三处一起还原才红。
判据：**变异之后先问「这真的是改动前的状态吗」，再去跑。**

**断言「结果相同」拦不住「过程不同」。** 本轮两次实测：

| 变异 | 当时的断言 | 为什么拦不住 | 改成什么才拦住 |
|---|---|---|---|
| M32 把进度回调挪到循环外 | 「报了几次 ≥ 2」+「最后是 (N,N)」 | 「起步报一次 + 末尾报一次」正好满足 | 断言中间值 `(500, 501)`；**该用例后来又收紧成整条序列 `[0..N]`**——「有中间值」还拦不住**按批报**（M33，见 §二十七） |
| M34 去掉一次性迁移的 guard | 「第二次调用返回 False」 | 没有 guard 时第二次同样会因为「已经一致」返回 False | 摆正后再塞一条不一致的，看它动不动手 |

判据：**断言要挑「只有正确实现才会出现的差异」**，而不是「两种实现都给得出的结果」。

**变异写得过重，红的理由就不指向被测对象。**
M17 第一版从 INSERT 的列名里删了 `star_basis`，却**没同步占位符数量** →
参数个数对不上 → **六条一起红**，全都不是这条要测的东西。改成
「表里有列、只是不写它」（列名 / 占位符 / 元组三处一起改）才只剩该红的两条。
**红的用例集合与预期不符时，先怀疑变异写坏了，再怀疑被测代码。**

## 十三、前端改动的四个静默坑

改弹窗/抽屉这类 UI 时，有四种情况是「代码写了、build 也过了，界面上却没生效」，
共同点是**都不报错**：

1. **父容器没有确定高度时，`height: 100%` 等于没写。**
   把 `.el-dialog__body` 改成 `overflow: hidden` 去做「多列各自滚动」，必须先给
   `.edit-dialog` 一个 `height`——只写 `max-height` 不够（那时弹窗高度是「内容撑开」，
   父高为 auto，高度链条 body → el-row → el-col 从头就断，独立滚动建不起来）。
   而 `overflow: hidden` 会把超出部分**直接裁掉、连滚动条都没有**，被裁的正是排在最
   底部的那个卡片。**动 overflow 之前先确认父容器有确定高度。**
2. **el-dialog / el-drawer 是 teleport 到 body 的，组件内的 scoped 样式够不到它内部。**
   改它们的内边距、布局要写进全局 `frontend/src/styles.css`，并用 class 前缀限定、
   别污染其它弹窗。本项目已为此把 `.dot` 系列样式上移到全局一次。
3. **scoped 规则与全局规则特异性相同时，胜负取决于注入顺序。**
   `.source-tabs[data-v-x]`（0,2,0）与 `.edit-dialog .source-tabs`（0,2,0）同级，
   想稳定覆盖就**多带一级选择器**拿到 0,3,0。
4. **Vue 模板里直接写引擎字面量（`{{ }}`、`<js>`）会被解析掉**——前者当插值、
   后者当标签，而且**转义成 HTML 实体也救不回来**（编译发生在实体解码之后）。
   要原样显示这类清单，用 `v-pre` 让整段跳过编译。

-> 第 2 条（scoped 样式够不到 teleport 出去的弹窗）已提炼为 AGENTS #14

## 十四、App 调试的 tag 是「去 App 库里查」，不是「告诉它跑哪个源」

**症状**：新建的源、或改了规则还没导进 App 的源，点「连 App 调试」什么都不发生，
等满超时才失败；已导入的源却正常。同一个按钮两种结果，失败时还没有任何提示。

**根因**：调试 WS 收到 `{"tag", "key"}` 后执行的是
`appDb.bookSourceDao.getBookSource(tag)?.let { startDebug(...) }`
（`BookSourceDebugWebSocket.kt:39`），而那条查询是
`select * from book_sources where bookSourceUrl = :key`——**精确字符串匹配**。
查不到就什么都不做：不发消息、不报错、不关闭连接。

推论有两条，都不是「用错 API」而是用法本身的前提：
- **新源没法用 App 验证**，除非先把它导入 App
- **规范化过的 URL 一定失败**（正是 core/loader.py 那 20.7% 差异的后果）

**结论**：App 的 Web 服务不只开调试 WS，还开着一组 HTTP 接口
（`KtorServer.kt:57,121`，端口 = WS 端口 - 1）。其中
`POST /saveBookSource`（body 是单个书源裸 JSON；App 侧 `insert` 是 **REPLACE**，
幂等）与 `GET /getBookSource?url=` 正好补上这个缺口：

- 调试前先查一次 → 把「静默无响应」变成 `unreachable / missing / ready` 三态
- 缺源就推一次 → 把当前表单（含未保存改动）发过去再调试，省掉
  「保存 → 导出 → 扫码 → App 导入 → 才能调试」的整圈往返

**代价要讲清楚**：推送会改动用户 App 里的书源数据（同 URL 覆盖）。边界是
**只能在用户主动发起调试、且明确确认之后**、由预检结论决定要不要推——不得有
后台的、没人触发或没问过用户的推送。**「调试」和「往 App 里写」是两件事**：
把推送做成点「调试」的隐式副作用，用户点的是调试、App 里的数据却被改了，而这在
界面上完全看不出来（这一版最初就是这么写的，是用户指出来的）。做成「一个按钮 +
只在需要推送时弹一次确认」，比摆两个按钮好——用户不必先判断自己属于哪一种。
接口细节写在 `core/app_debug.py` 的「HTTP 接口」一节，不要在这里抄第二份。

**但只判断「源在不在」是不够的**——那会漏掉**「App 里有，但是旧版本」**：
预检若只做 presence 检查，这种情况会判「可以调试」，而调试跑的始终是 App 里那份，
于是结果看着正常、答的却不是你在改的东西。这是本类工具最容易骗到人的地方
（和「静默无响应」是同一个坑的另一面）。所以预检要拿本地那份和 App 返回的那份
**比对规则**，把状态分成 `missing / stale / ready` 三档。

比对有个坑：**别用 `loader.fingerprint()`**。它把整个 `ruleSearch`/`ruleToc`/
`ruleContent` 字典都算进哈希，而 App 存的是它自己的实体——Gson 会丢掉我们多给的键、
补上它自己的默认值，字段集合本就不同，拿指纹比必然每次都判「不同」，白覆盖一遍。
只比调试真正会跑到的、双方都一定有的那几个字符串字段。

**顺带**：`run_app_debug` 的返回体一直带 `events`（App 推的原始事件流，含耗时），
前端却从没渲染——要查「App 到底推了什么」只能去跑 `tools/probe_app_debug.py`。
「后端返回了、前端从来不消费」也是一种静默失效。

## 十五、concurrentRate 是 String 不是 int，而且我们曾经把它抹成 0

**症状**：源自己声明了 `concurrentRate`（就是「这么打我你会被封」），我们不但不遵守，
还在导入/保存时把它**静默抹成 0**——0 在 App 里等于「不限速」。

**根因**：`core/sanitize.py` 把它列进了 int 字段清单，于是 `"1/2"` 走
`int(float("1/2"))` 抛异常、被兜底成 `0`。而这个字段在 Legado 里是
**`String?`**（`BaseSource.kt:35`），两种写法都合法（`ConcurrentRateLimiter.kt:82`
的注释：「并发控制为 次数/毫秒，非并发实际为 1/毫秒」）：

    "n/m"   n 次 / m 毫秒
    纯数字 x  1 次 / x 毫秒

这类破坏**会把自己的证据一起抹掉**——库里存量的 `"1/2"` 早就变成 0 了，事后无法反推
到底破坏了多少条。当时的 3861 个源里 `"n/m"` 写法是 0 个，但那不代表没发生过。

**结论**：三条一起修，缺一不可：

1. `sanitize` 只把纯数字归一成 int，**非数字串原样保留**（`"1/2"` 是合法值，别碰）
2. `checker._request` 发请求前按源声明的间隔等一下（异步 `_throttle`）。源内请求本来
   就是顺序的，不需要锁
3. **`core/fetch.py` 也要限速**（同步 `_throttle` + 模块级状态 + `threading.Lock`）。
   四条抓取链路里只有 checker 走 aiohttp，其余三条——全链路试跑、连 App 调试补抓页面、
   快速新增源——都走这里。漏掉它的后果不是"少遵守一点"：`repair_many` 是自动批量的
   （`Semaphore(4)` + `gather`，默认 3 轮 × 每轮最多 3 次抓取 = 单源最多 9 次），
   而修复的目标恰恰是失效源。**只给 checker 加限速 = 批量校验守规矩、AI 修复连打九下。**

解析口径（`rate_interval_ms`）放在 `core/quality.py`，两边共用同一份——`fetch` 不该
反向依赖 `checker`（§十）。解析不了就不限速：宁可多打几个请求，也不瞎猜一个间隔把
正常源拖慢。

**`"n/m"` 是有意近似**：App 是窗口/突发语义（n 次可以连着发完再等），我们折算成均匀
间隔，总速率一致、突发形状不同（更严格）。别当成"和 App 一模一样"来依赖。

**已知未覆盖**：`fetch._throttle` 的锁只做了逻辑正确性，没写并发用例（那种用例容易
抖动）。去掉锁或把 sleep 挪进锁里，现有测试都不会红。

**顺带记一条测试基础设施的坑**：`tests/test_checker_judge.py` 会用空壳模块顶掉
`sys.modules["aiohttp"]`，那是**全局副作用**。新加的测试如果真去调
`AsyncChecker._request`，单独跑没事、全量 `discover` 时会在
`except aiohttp.XxxError` 求值处抛 AttributeError。涉及 aiohttp 的断言要么别依赖
返回值，要么把环境差异考虑进去。

（**补记**：那个桩后来删了——aiohttp 是 pyproject 里的硬依赖，「隔离未安装的可选
依赖」这个理由不成立，而它坑了两次。测试文件里凡是往 `sys.modules` 塞东西的，
都要意识到那是全局的。）

## 十六、校验「请求成功但状态不变」——三处错凑在一起

**症状**：界面点校验，任务跑完、提示成功，列表里的健康度/星级纹丝不动。
而且有效期内的缓存好像也从来没被复用过。

**根因**：三处，各自都能独立成立，凑在一起才让现象这么难猜。

1. **`run()` 里保存那一段被 `if self.cache_dir:` 挡住**。Web 那条链路
   （`backend/api/ops.py`）构造 AsyncChecker 时传的是 `use_store=True`、
   **不传 cache_dir**，于是整段保存被跳过——算完就丢。
2. **`save_cache_append` 又是先 `os.makedirs(self.cache_dir)` 再判 `use_store`**，
   cache_dir 为 None 时第一步就抛 TypeError。所以就算过了第 1 关也会崩。
   两处是同一个故障的两半，**只修一处仍然坏**。
3. **缓存的键两侧口径不一致**：`Store.save_checks` 存的是**规范化**后的 URL
   （`checks.source_url`），而 `run()` 拿 `record.url`（抓取时的**原文**）去查——
   尾斜杠一类的差异就查不到。这不是「少命中一点」，是**store 后端永远命不中**
   （这个差异本项目实测 20.7%）。就是 §五 那条「跨表/跨库关联的 URL 两侧必须用
   同一套规范化」，只是方向反过来：那次是写侧没归一，这次是读侧。

**结论**：三条都修了，并且都补了离线用例（`tests/test_checker_persist.py`）。
另有两条顺带：

- **写缓存失败不能 `except Exception: pass`**。写不进去的表现是「校验跑了但状态
  不变」，和「源本来就没变」在界面上**完全无法区分**。现在计数 + 收尾打印
  （`save_failures`），任务结果里也带出去。
- **「复用了几条」要报出来**（`cached_count`）。不说的话，「点校验 → 完成」和
  「一条请求都没发」长得一模一样——用户会以为校验过了，其实只是读了缓存。

**推论**：一道门的条件写错（`cache_dir` vs `use_store`），表现可以完全不像「保存
失败」，而像「这个功能本来就不生效」。凡是「A 生效了但 B 没变」的问题，先怀疑
**从 A 到 B 之间那道条件判断**，而不是 A 本身。

## 十七、合并配置时 `None` 是「没传」，`False`/`0`/`""` 不是

**症状**：校验参数支持了「全局默认 + 本次覆盖」之后，用户明确把某个开关关掉
（当时是 `probe_search`，现已并入探测深度；同理 `verify_ssl`）、或明确把代理清空成
直连，结果**参数看起来没生效**——校验还是照常探测搜索、还是走了代理。
界面上没有任何异常，日志里也没有。

**根因**：合并写成了 `payload.get(key) or 全局值`。`or` 对 `False` / `0` / `""`
一律当成「没传」，于是这三种覆盖被**静默吃掉**，回落到全局值。

判据必须是 `is not None`：`False`（关掉证书校验）、`""`（本次直连）、`0`
都是**有意义的值**，只有 `None` 才表示「没传」。
（见 `core/settings_store.resolve_check`；`tests/test_settings_store.py` 里
「keeps_false_and_empty_string」与「none_means_fall_back_to_global」**必须成对存在**——
单独任何一条都拦不住把两者互换的写法。）

**推论**：凡是「默认值 + 覆盖」的合并，先问清楚**用什么表示『没传』**，然后让
它和「传了个空值」在代码里长得不一样。`or` 是最容易把这两件事混起来的写法。

## 十八、判定输入里不能放「我们自己写进去的结论」

**症状**：`reclassify` 的类型判定与源的实际类型系统性不符，漫画站被判成小说；
而且**改不动**——`--write` 改对一批，下次再跑又变回去。看症状像 §四
「类型必须实测，不能信声明值」，但把声明值全清掉，判定照样偏小说。

**根因**：`reclassify._text_of()` 把 `bookSourceGroup` 整串当特征文本读，而这个
group 是 `organizer.group_title` / `store._system_group_for` **按 `bookSourceType`
生成**的，形如 `📖小说,待验证`。于是形成闭环：

    类型错(默认 0) → group 写成「📖小说」 → 命中文本特征 "小说" → novel +3
                  → 单独就到阈值 3 → 再判成小说   ↺

错的标签**自我固化**，永远纠正不过来。实测：命中 "小说" 的 3540 条源里，
**3506 条的 group 带着系统类型标签**（字段分布上 group 单独占 2290 条）；
剥掉系统标签后 **119 条改判**——58 条 `小说→-1`、32 条 `小说→漫画`，
外加 20 条 `漫画→-1`，**循环在反方向同样成立**。

**结论**：判定输入里只能放**原始观测**，不能放「我们自己写进去的结论」。
`_text_of` 现在只取 group 里的**用户标签**（`core/tags.py:extract_user_tags_from_group`）
——那是人主动打的，是真信号；系统标签是派生物，一律丢掉。

> 注意这里是「症状对、归因错」的典型：原判断说的是「`NOVEL_TEXT_HINTS` 含
> `阅读`/`txt` 这类泛词，中文小说站几乎必中」，而实测这三个词各自只影响 **4~5 条**。
> **归因必须靠数，不能靠像**——症状指对了方向，不等于指对了原因。

**推论**：凡是出现「A 的输出被写回 A 的输入」，先问这个字段是**原始数据**还是
**我们的结论**。归档 / 整理 / 标注类功能最容易造这种环——分组、缓存、指纹、
报表、质量标签全是候选。判据要经得起「把派生字段全清掉，结论还成立吗」。

-> 已提炼为 AGENTS #10

**变异要成对**：这次的两条变异 `M6 还原循环`（三条循环用例红）与
`M7 把 group 整个丢掉`（反向断言 `test_user_tags_still_count` 红）是一对。
只做 M6 会让人以为「全丢」也行——**修过头的方向也得有一条断言拦着**。

## 十九、读一个不存在的字段 = 死代码，而它看起来像信号

**症状**：`infer_type_static` 里有一条「有 `ruleContent.image` 图片规则 → 漫画 +3」
的信号，权重高得足以单独定案。它**从未执行过**。更麻烦的是，测试里有一条断言
把这个不存在的信号钉死了，读起来像「这个信号是有效的，只是权重值得商榷」。

**根因**：`ruleContent.image` 在 Legado 的 `ContentRule` 里**不存在**——图片走
`content` 规则本身（`looks_like_image_rule` 判的就是它）。本项目也从不写它：
实测库里的 **3861 条源，该字段非空的是 0 条**。于是 `image_rule.strip()` 恒为假，
`if image_rule.strip(): manga += 3` 是死代码，`:112` 那个
`and not image_rule.strip()` 也永远是 `True`。

危险**不在算错**（它算不出错，因为它根本不算），而在于**它读起来像一个存在的信号**：
有人会照它去调权重，或者以为「图片源有救了」。

**结论**：删掉，并在原处留一行说明**为什么删**，避免被重新引入。删的同时必须
处理那条钉死旧行为的断言——它会把死代码伪装成活的。这次是
`test_image_rule_worth_three` → `test_rule_content_image_is_not_a_signal`
（改成的断言是「带这个字段的源必须和不带时判得一样」）。

-> 已提炼为 AGENTS #11

**推论**：判断一段代码死没死，**别靠读，去数**。这次是一行搞定的：

    sum(1 for s in d if str((s.get("ruleContent") or {}).get("image") or "").strip())

结果是 0，读半小时代码也不会比这更确定。同类可疑字段（本项目还有
`ruleContent.webView`、`bookSourceType == 4`）都该这么过一遍再决定动不动。

## 二十、文档会自己腐烂：一处写，别处只留指针

**症状**：`TODO.md` 在两周里被反复订正——同一个条目的状态改了三次，
每次都要**重新核对代码**才知道它到底做没做。有一份设计文档记的是「已做完」的事，
把它当待办看就会白做一遍。

**根因**：那份文件同时装了两类**寿命完全不同**的东西：

| 类型 | 例子 | 寿命 |
|---|---|---|
| **待办** | 「末段语义要修」「试跑要带 cookie」 | **做完就该删** |
| **知识** | group 循环的机制、`getElements` 与 `getStringList` 的区别 | **要长期留** |

待办混进知识库会**立刻过期**（做完的条目还留着，下次翻到以为没做）；
知识混进待办清单会**跟着被删掉**。所以「怎么订正都还是不对」——
不是写得不认真，是**它的定位本身在漂**。

**结论**：文档按**性质**分层，不按重要程度（重要程度只决定要不要收）。
判据写进了 `AGENTS.md` 硬性约定 #9：约束进 AGENTS、论证进 lessons、
用法进 README/WORKFLOW、待办进 `TODO.md`。**一处写，别处只留指针。**

**推论一：这已经是同一条原则在本仓库的第三次应验。**

- `AGENTS.md` #7：系统标签枚举只在后端定义——两边各存一份，书源类型就漂成过视频
- #8：校验参数的默认值只在 `settings_store` 定义——三处各写一遍，界面上改不动
- #9：**文档**也只有一个事实来源

代码里的枚举、配置的默认值、文档里的知识——**形状不同，病是同一个**：
`同一个事实存了两份，就一定会漂`。认这个形状，比逐条记规矩省事。

**推论二：待办要按「现在还能触发吗」过，不是按时间过。**

「试跑不带 cookie」这条在写的时候是真的——那时编辑弹窗还有本地离线试跑。
后来那个入口撤了（调试只剩「连 App」，cookie 由 App 自己的 CookieJar 管），
**这条的前提就没了**，而条目还留在清单上，看着像一件该做的事。

**能力撤了、条目还在**，是待办清单特有的腐烂方式——按时间排序看不出来，
按「现在还能触发吗」一问就问出来。

**推论三：元知识也要入库。** 上面这套「文档怎么分层」本身也是知识——
「约束进 AGENTS / 论证进 lessons」是**规矩**（进了 AGENTS #9），
「为什么会腐烂」是**论证**（就是本节）。分层规则自己也要遵守分层。

-> 已提炼为 AGENTS #9（文档也只有一个事实来源）

## 二十一、测试要防的是「形状」，不是「这一条」

**症状**：给 `checks` 表加 `star_basis`，四处（DDL / `NEW_COLUMNS` / `save_checks`
的 INSERT / `checks_map`）都得改。补了「往返测试」和「列名对得上」两条断言，看着很稳——
而**造变异时我自己漏改了 `NEW_COLUMNS`，整个测试文件仍然全绿**。

**根因**：那两条断言用的都是**全新的库**：DDL 直接把列建出来，**根本走不到
`NEW_COLUMNS` 那条路径**。而真实用户的库是旧 schema，补齐靠的正是它。

同类：迁移测试的 fixture 一开始随手编了个「最小表」（只 7 列），结果视图建不起来
（引用了 `probe_depth`）。**那些列本来就不该在 `NEW_COLUMNS` 里——它们是老版本就有的。**
判据是「哪些列是后来补的」，不是「哪些列我懒得写」。

**结论**：

- 加一个跨层字段时，**结构性断言要覆盖两条路径**：新建的库 + 从旧 schema 迁移的库
- fixture 要构造**真正的老状态**（「现在的 DDL 减去 `NEW_COLUMNS`」），不是最小可用集
- 更好的做法是写**结构性断言**而不是逐列断言：「`save_checks` 写入的每一列表里都必须有」
  （正向）+「表里每一列都必须被写过」（反向，排除自增 id）。逐列补只能防住**已经踩过**
  的那些，而这类事情的形状永远是同一个——**加了一个字段，忘了在其中一处落库**。

**推论**：与 §十二 是同一课——**测试的价值在于它拦住了什么，不在于它写了多少**。

## 二十二、归因必须靠数，不能靠像

**症状**：`reclassify` 的类型判定系统性偏「小说」，漫画站被判成小说。
原判断写的原因是「`NOVEL_TEXT_HINTS` 含 `阅读`/`txt` 这类泛词，中文小说站几乎必中」。

**根因**：那个归因**是猜的**。实测逐词移除后的改判数：`xs` 5 条、`阅读` 4 条、
`txt` 1 条——三个目标词加起来 **10 条**。而真凶是 **`小说` 一个词影响 143 条**，
且它不是「泛词」，是**分组标签的自固化循环**（见 §十八）。

**结论**：**症状指对了方向，不等于指对了原因。** 归因要落到可测量的东西上：

    # 一行就能证伪一个猜测
    sum(1 for s in d if ...)

**推论：注释与代码不一致时，信代码。** `_classify` 的注释写着「其他 2xx/3xx 视为可达」，
而代码是 `return Health.OK`——**没有范围判断**，404 / 400 / 410 / 451 全被判成「可用」
（实测库里 91 条 `ok` + 4xx）。注释描述的是**意图**，代码描述的是**行为**；
两者矛盾时，坏掉的是行为，修的时候两边都要改。

## 二十三、同一件事可能走两个函数

**症状**：`class.chapter-list@tag.a` 这类规则，我按源码推断「末段会被当属性名 → 取空」，
于是判定我们的解析器**误放**，还估了 3441 条的规模。而在 App 里实测，
**它能出章节**——结论被当场推翻。

**根因**：**读错了函数。** Legado 对两类规则走的是两条不同的路径：

| 规则种类 | 走哪个函数 | 末段怎么解释 |
|---|---|---|
| 列表（`chapterList` / `bookList`） | `getElements`（`BookChapterList.kt:203`） | **每个 @ 段都是选择器** |
| 取值（`content` / `intro` / `author`…） | `getStringList` → `getResultList` → `getResultLast` | `when` 只认 text/textNodes/ownText/html/all，**其余当属性名** |

所以「末段是动作」只对**取值类**成立、对列表类不成立——两件事都对，不矛盾。
影响面也从 3441 条缩到 **290 条**（只有取值类字段）。

**结论**：**「实测推翻了源码结论」时，先确认两边说的是不是同一条代码路径。**
反例和结论如果走的是不同的函数，那个反例什么也证明不了。

## 二十四、流只是加速手段，真相要在可查询的地方

**症状**：点「全量校验」后界面卡在「正在校验 1 条」，校验按钮永远点不了，只能刷新页面。
（另：一次 3 分 47 秒的全量校验，界面上**全程显示 0**。）

**根因**：两处，各自独立：

1. `subscribeJob` 的 `es.onerror = () => es.close()`——**那一句把 `EventSource`
   自带的重连关掉了**。而服务端本来就是按「状态」设计的（每次连接的第一帧就推当前
   全量），**重连一次就等于补齐终态**。关掉重连之后，一次网络抖动就永久失联，
   而调用方的 `checking` 挂在流的终态上，于是永远不复位。
2. `run()` 里的进度**只 `print` 到控制台**，从不写进 `jobs.progress`；
   结果也是**全部跑完才落库**。于是长任务在界面上没有任何中间态。

**结论**：**只要「UI 状态对不对」依赖于「某条消息一定送到了」，就一定有卡死的窗口。**
这不是 SSE 的缺陷，是**把一次性事件当状态用**的缺陷。

做法：`onerror` 不立即关闭（让它按默认节奏重连）+ **重试上限** + **上限到了也必须
复位调用方的状态**。最后一条才是真正防卡的出口——无论发生什么，它都得有出路。
长任务的进度要写进**可查询的地方**（`jobs.progress`），不能只打印。

## 二十五、三处静默失效：类型、字段、空串

三个都是「不报错、只是结果不对」，而且都发生在**跨层的边界上**。

**① 类型不匹配：`0/1/null` vs `true/false/null`。**
列表 API 的 `toc_complete` 来自 SQLite 的三态整数（`0/1/null`），而校验结果里是
Python bool（JSON 化成 `true/false/null`）。前端模板判的是 `=== 1`——`true` 进去
两个分支都不成立，**那一格永远显示「未验证」**：看着像没校验，其实是类型不对。

**② `response_model` 会静默裁字段。**
后端新增了字段但没加进 pydantic 模型 → FastAPI 按模型裁剪 → 前端永远拿不到。
**看起来像前端 bug**，查半天才发现字段在传输层就被丢了。

**③ 补列之后的空串「小于任何时间戳」。**
给 `jobs` 补 `expires_at` 时，老行的值是 `''`（ALTER 的默认值）。而
`'' < '2026-09-16 ...'` 在**字符串比较**下为真 → 清理任务一跑就把历史任务全删了。
必须**按 `updated_at` 回填**，等价于「从最后一次更新算起还有 N 天」。

**结论**：跨层传数据时，**两边都要显式对齐**——类型、字段名、空值的语义。
三处的共同形状是**边界上的一次隐式转换**，而隐式转换不报错。

## 二十七、空闲连接池没有上限，而 Windows 的 select() 有 512

**症状**：全量校验跑到一半，整个后端进程带着 traceback 死掉，最后一行是
`ValueError: too many file descriptors in select()`（栈顶是 `asyncio/selectors.py`）。
日志停在哪一条是随机的——本次是「进度: 500/3861」。

**根因**：两件事凑在一起，单看每一件都正常。

1. **aiohttp 的 `limit` 只管「在飞」的连接。** `_release` 之后连接会留在
   `connector._conns` 里等复用（默认 keepalive 15s 才回收），而**那份池子没有任何
   总量上限**（`aiohttp/connector.py` 的 `_release` 与 `_cleanup`）。校验扫的是
   2562 个不同主机（库里 3861 条源），每条源一个连接，池子于是随进度单调上涨——
   实测 20 并发跑 200 个主机，池里躺着 **182 个空闲连接**、事件循环注册了
   **199 个 socket**，远超并发上限 20。
2. **`--reload` 起的后端跑的是 SelectorEventLoop。** uvicorn 只在**非**子进程时
   才给 Windows 上 Proactor（`uvicorn/loops/asyncio.py:9-11`），而 reload 走的是
   multiprocessing 子进程（`Process SpawnProcess-1`）。Windows 的 `select()` 上限是
   **512 个 fd**，一超就抛异常并**带走整个进程**——崩在 500 条正是池子堆到 512 的
   那一刻。

**结论**：多主机扫描一律 `force_close=True`（`core/checker.py` 的 `run()`、
`core/reclassify.py` 的 `_diagnose_all`）。跨源复用本来就少（65% 的主机只有一条源，
最多的 11 条），丢掉的只是同一源内部几个请求（域名→搜索→详情→章节）之间的复用，
换来的是「同时打开的 socket 数**恒定不超过并发上限**」这个硬保证。

**复现方式**（几行就够，别靠猜）：本地起 N 个端口的 HTTP 服务，用 `TCPConnector`
的同一套参数跑 N 个不同端口的请求，打印 `len(loop._selector.get_map())`——修复前
它随请求数线性上涨，修复后贴住 `limit`。

**推论**：
- **`limit` ≠「同时打开的连接数」**，它是「在飞」。凡是「连接数超标」的排查，都要
  看池子里**空闲**的那部分，而不是那个参数本身。
- 报错落在 `asyncio/selectors.py` **不代表是 asyncio 的问题**。先问「谁把 fd 堆到了
  512」，再问「为什么不回收」。
- 同一份代码在 `--reload` 与不带 `--reload` 下跑的是**两个事件循环**，只在其中一个
  上崩是正常的。这类环境差异要有意识地想到——尤其当「明明是同一份代码」。
