# 本项目的架构决策与踩坑记录

每条都按「症状 → 根因 → 结论」写。改动核心逻辑前请先扫一遍。

> **编号是历史编号，跳号是删并小节留下的空位**（六 / 二十五 / 二十九 / 四十一 /
> 四十二 / 四十五）：不要复用这些号，也别去补——引用一律用现存的号。

## 一、规则回放器必须和 Legado 语义一致

**症状**：脚本验证通过的源，导入 App 后不能用；反之 App 能用的源被判失败。

**根因**：早期那版规则解析只做（**那个名字今天还在**：`replayer.extract_all`，
`checker` 侧以 `apply_css_rule` 为别名在 import——别照着本节去搜同名函数删除）

    selector, _, attr = rule.rpartition("@")   # 取最后一个 @
    soup.select(selector)                      # 然后 el.get(attr)

它**不支持 Legado 的 `class.` / `tag.` 前缀简写、`##正则##替换`、`@js:`、JSONPath**。
一条 `tag.a@text##作者：##` 的规则会被当成属性名 `text##作者：##`，取到空字符串——
于是「内容为空」被误判成「规则失效」。

**结论**：验证器和执行引擎必须是同一套语义。规则解析统一走
`core/rules/replayer.py`，且**不支持的语法要返回明确原因**，
由调用方判为「无法验证」而不是「失效」。误杀比漏放更贵。

## 二、静默失败：四种面孔，一条规矩

共同形状：**不报错、只是结果不对**，且都发生在跨层边界上（吞异常、隐式转换、
跳过不记）。

**① 异常被吞成「无法验证」。** `requirements.txt` 漏了 `beautifulsoup4`，那行 import
写在 `try` 之外，上层 `except Exception` 一吞，结果全变成「无法验证」——
`toc_complete` / `content_ok` 全是 `None`，看着像深度验证没查出来，**实际一个额外
请求都没发**；连带 `_confirm_hit` 的异常分支返回 `True`，命中判定退化成「响应体里
出现关键词就算命中」。

**② 跨层隐式转换**（三处，都不报错）：

- 类型：`toc_complete` 从 SQLite 出来是三态整数 `0/1/null`，校验结果里是 Python
  bool，前端判 `=== 1` → **那一格永远显示「未验证」**，看着像没校验。
- 字段：后端新增字段但没加进 `response_model` → FastAPI 按模型裁掉 → 前端拿不到，
  看起来像前端 bug。**两次踩中**：`star_basis`、`jvm_state`（S2 来源阶梯列，
  服务端 enrichment 明明算出了 3774 条，HTTP 响应里却全空；先是疑心数据侧，
  又疑心没生效的旧进程，实际响应模型里没有那三个字段）。同一处代码里
  `star_basis` 的注释就写着这条，但**注释管不住下一次新增字段**——
  防回归要靠形状测试，不是靠注释（见 §二十一）。
- 空串：给 `jobs` 补 `expires_at` 时老行是 `''`，而 **`'' < '2026-09-16 ...'` 在
  字符串比较下为真** → 清理任务一跑删光历史任务。回填必须按 `updated_at` 算。

**③ 跳过不留痕。** 补抓页面时 `if not url: continue` 连一条 note 都不留（正文规则
为空时 App 不发请求，事件里就没有 URL）→ 抽屉里「整页源码」一片空白、**没有任何
解释**，用户以为功能坏了。配套：诊断按成因分类（没有页面 / 页面上没有目标节点 /
规则为空 / 回放不了 / 0 命中 / 取到但不达标），**每类的下一步动作不同**。

**④ 留痕与复用绑在同一个开关上。** `should_cache_result()` 想防「一次断网污染后续
校验」，却顺手把**落库**也禁了；而列表是按「有没有 checks 行」算「未校验」的 →
1222 条源永远显示「未校验」，每次全量还要重打一遍。拆开：**照写，但绝不复用**
（复用的门在 `is_cache_item_valid` 的 `is_inconclusive`）。

**规矩**：

- 所有「无法验证」的返回路径都要能说出原因（`err` / `fail_reason` 一路透传到报告）；
  **异常吞掉之后必须留下痕迹**；每次「因为条件不满足而跳过」都要说清为什么跳过。
- 跨层传数据，两边都要显式对齐：类型、字段名、空值的语义。
- **「记录发生了什么」和「由此推断什么」是两件事**，别用同一个开关控——收紧其中一个
  的理由会静默地把另一个也收紧，而失去记录的代价要过很久才看得出来。

## 三、失效必须分桶，不能只有一个 DEAD

**症状**：报告里 `❌失效` 一大堆，人没法判断哪些该删、哪些该修。

**根因**：`checker` 只判「域名通不通 + 搜索有没有命中测试词」。
三种完全不同的情况挤在一个桶里：

- 域名注销的死站（该删）
- 域名活着但页面改版、规则过期的源（**可修，不该删**）
- 域名活着但已转型的站点（该改类型）

**结论**：拆成四类归因——`死站` / `规则漂移` / `站点转型` / `需登录`（2026-09 前叫「需验证」）。
判据是「域名可达性 × 反爬特征 × 搜索页能否解析 × 实测类型」的组合。
`diagnose` 命令就是这个设计的实现。

## 四、类型必须实测，不能信声明值

**症状**：明明是漫画站，被标成小说源。

**根因**：`add` 命令的类型来自 `--type`（默认 `novel`），
`bookSourceType` 从未被实测校验过。默认值一路写进库。

**结论**：`reclassify` 用「静态信号 + 首页/正文实测」反推类型：
域名/名称关键词、正文规则取的是图片还是文本、`imageStyle=FULL`。
（**别按 `ruleContent.image` 加信号**：那字段不存在，见 §十九。）累计打分 ≥3 且高于另一方向才改判，否则保持原样。
**实测优先于声明。**

## 五、URL 必须规范化后再作为 key

**症状**：迁移后 `v_sources` 里 571 个源查不到校验记录，
健康度分布比报告少 571 条。

**根因**：`upsert_sources` 存的是 `_normalize_url(bookSourceUrl)`，
而 `save_checks` 存的是缓存里的原始 `url`。两者不是同一个字符串，
SQL JOIN 自然对不上。

**结论**：**任何跨表/跨库关联的 URL，两侧都必须用同一套规范化函数**
（`core/loader._normalize_url`）。这类 bug 不会报错，只会静默丢数据——
所以**迁移必须做一致性校验**（源数/类型/健康/星级四项分布对比），
不做这步它就一直藏在库里。

**同一个坑犯过两次**：缓存去重键（`load_cache`）也曾按原始 URL 去重，
两个目录 10166 条归一后只剩 5591 条（4575 条是同一站点的 URL 变体）。
→ **任何以 URL 为键的地方（表、缓存、去重、对账）都要过同一个归一函数。**

## 七、SQLite 而不是 MySQL


**理由**：单用户本地工具。标准库自带、零运维、单文件、`VACUUM INTO` 就能备份。
几万条源 + 校验的量级离 PostgreSQL/MySQL 的合理起步差几个数量级。

**关键约束**：**DB 文件不能放网络盘（SMB/NFS）**——SQLite 依赖文件锁，在网络挂载上
会**静默损坏**。服务跑在 NAS 上时，DB 放 NAS 本地卷，只有备份产物放网络盘。

**什么时候才该换**：多机多人同时写 / `busy_timeout` 频繁超时 / 单库到几十 GB。
单机单用户碰不到。PRAGMA（WAL、busy_timeout 等）见 `core/store.py`，那里是唯一实现。

## 八、同一份状态别散在多个 store 里


**症状**：一个源的信息散在多处——`candidates.json`（规则 / 分组 / 类型）、管理库
`sources.sqlite3`（校验 / 任务），一度还有第三个导入台账库。改一处忘另一处，就会出现
「列表显示 A、详情显示 B」。

**做法**：**能用一张表 + 视图表达的，不要靠代码 merge**（`organizer.py` 曾经存在的
意义就是把三处拼起来，merge 逻辑本身就是 bug 温床）。校验那条已经收拢：`checks` 表 +
`v_sources` 视图 LEFT JOIN 最近一次。

**第二份曾经存在，已于 2026-09-19 删除**：`core/registry.py` 用**裸 sqlite3** 另建了一个
导入台账库（`book_sources.sqlite3`，CLI 的 `import-sources` / `review-imports` 走它），
而 Web 端导入（`backend/api/imports.py`）写的是管理库——同一件事两条实现、两套存储。
删它的**直接证据是那个库文件在本机根本不存在**：跑一次 CLI 导入会在 cwd 新建一个空库，
没人读；而且它的「批准」写回的是 `candidates.json`，那已经不是事实来源（AGENTS #2）。
→ **判据：同一份状态出现第二个存储时，先问它是不是已经没人读了**；是，就删，别维护两套。

## 九、AI 只提议，验收必须由回放器做

**结论**：`repair` 的闭环是

    抓证据 → 模型提议 → legado_rules 回放验证 → 失败差异回喂 → 重试

让模型直接输出书源、然后相信它，和早期的启发式推断一样不可靠。
**验证证据要压缩**：把几 MB 的 HTML 压成 90 行缩进 DOM 大纲，
模型只做「修正」而不是「从零发明」选择器。

**两道必须有的拦**（都用 `replayer.rule_supported`，别另写一份判定表）：

- **当前值本地回放不了**（JS / 模板 / XPath）→ 不许覆盖。提示词明令模型别写 `@js:`，
  于是它会把一条**在 App 里正常工作**的 JS 规则换成 CSS；而 `all_ok` 只看回放结果、
  不看改了哪些字段，没有别的检查会拦。
- **提议值回放不了** → 不许落地。落地了本地就验不了它，而 `verify_chain` 对
  「回放不了」判 unknown（`ok=True`）——它会**假装成修好了**。

所以 `merge_proposal` 返回 `(源, 跳过清单)`，清单进报告：**不碰 ≠ 没问题**。

**呈现上「本地验不了」必须与「规则取不到值」分开**：前者只能连 App 试，后者才是
规则没写对。混成一句「没取到值」，用户会去改一条其实只是我们跑不了的规则
（同 §三十八：同一屏上的两个来源会互相打架）。

## 十、核心层不许反向依赖


**症状**：`checker.py`（核心）为了一个 `_abs_url` 依赖了 57KB 的 CLI 工具
`add_source.py`；`rate_interval_ms` 一度定义在 `checker` 里，`fetch` 要用就只能反向依赖它。

**结论**：**依赖方向只有一条：CLI/服务 → core，core 不许回头依赖 CLI 或调用方。**
共用的小函数抽成独立模块（`core/urls.py`、`quality.rate_interval_ms`），
需要「同一份定义」的东西一律上移，不下沉。

**已知的两处例外（2026-09-20 实测，别当成漏网之鱼去「修」）**：
`core/repair/evidence.py` 与 `core/repair/loop.py` 各有一处**函数内惰性 import**
`services.add_source`（复用 `verify_chain` 做证据链）。它们是有意破环、不是待清理的
违规：修的方向是把 `verify_chain` 上移进 core，属重构不是清理。**除这两处外仍是硬约束。**

## 十一、验证手段的优先级


1. **单元测试**（离线、可注入假依赖）——`repair` 循环那套就是用假 LLM + 假验证器
   在离线状态验完整闭环，不联网就能跑
2. **import 冒烟**——改完立刻 `python -c "import 模块"`
3. **真实联网跑小样本**——最后才做，且**比分布不比逐条**（网络有抖动，
   逐条比对会把抖动当成回归）

## 十二、变异测试会把中间态提交进去

**症状**：HEAD 上出现一个自相矛盾的提交——`PAGE_IDS["explore"]` 被写成 `"detail"`，
而**同一个提交里**的测试断言它必须是 `"explore"`。HEAD 全量 3 failures，工作区却是绿的。

**根因**：本项目的测试惯例是对新增用例做**变异测试**——临时把源码某一行改坏、跑全量
确认预期条数变红、再改回来，结果记进测试文件底部的变异表。变异态只存活几秒到十几秒，
而 **`git add` 抓的是磁盘当时的内容**，不是你以为的状态；那次提交恰好落在「改坏」的窗口里。
坑还不止于单人操作：本仓库出现过子任务与主会话同时改同一批文件、而且在做同一件事。

**结论**：做变异前先把当前状态提交成 WIP，或用 `git worktree` 隔离出干净副本再变异；
**变异窗口内绝不 `git add`**。多会话/子任务并行时，提交前先确认没有别的 writer 落在
同一批文件上。

**变异没变红时，先分清是哪种情况**：要么用例太弱，要么这是个**等价变异**（两条分支
在该输入下本就同判）。别默认前者、更别默认后者——去打印两边实际的返回值再定。
实例：把 `replay_step` 的列表分支改成一律走 `judge_content`，用例全绿；查下来是
下载源上两个 judge 都返回 unknown、短文本都判 pass。**只断言 `verdict` 的用例守不住
分支走错**，补一条断言 `reason` 的才红。

变异测试本身也别用「改完再改回来」的脚本 `write_text` 落地——见
`agent-write-safety` 里那条行尾陷阱。

**跑变异要带 `python -B`**：等长替换（`3`→`1`、`>= 5`→`>= 4`）不改变文件尺寸，
字节码缓存可能不失效，于是测试跑的是**上一轮变异**的编译产物。症状很坑——
报出来的确实是"✔ 变红了"，只是失败用例的名字和这个变异对不上（实测三条不同变异
报了同一个用例名）。看着通过、实则没测到，比不跑更危险。写变异脚本时顺手记下
每条变异**应该**让哪个用例变红，名字对不上就说明测量本身出了问题。

### 三条判据（都是实测踩出来的）

- **变异要能复现「改动前」**：同一处改动散在多个地方时，只还原一处 = 没测。
  先问「这真的是改动前的状态吗」，再去跑。
- **断言要挑「只有正确实现才会出现的差异」**：「结果相同」拦不住「过程不同」
  （「起步报一次 + 末尾报一次」也满足「报了几次 ≥ 2」）。
- **红的用例集合与预期不符时，先怀疑变异写坏了**：变异写重了（例如改列名却没同步
  占位符数量），红的理由就不指向被测对象。

-> 本节开头的「变异窗口内绝不 `git add`」已提炼为 AGENTS #14

## 十三、前端改动的四个静默坑

改弹窗/抽屉这类 UI 时，有四种情况是「代码写了、build 也过了，界面上却没生效」，
共同点是**都不报错**：

1. **父容器没有确定高度时，`height: 100%` 等于没写。**
   把 `.el-dialog__body` 改成 `overflow: hidden` 去做「多列各自滚动」，必须先给
   `.edit-dialog` 一个 `height`——只写 `max-height` 不够（那时弹窗高度是「内容撑开」，
   父高为 auto，高度链条 body → el-row → el-col 从头就断，独立滚动建不起来）。
   而 `overflow: hidden` 会把超出部分**直接裁掉、连滚动条都没有**，被裁的正是排在最
   底部的那个卡片。**动 overflow 之前先确认父容器有确定高度。**
2. **el-dialog / el-drawer 是 teleport 到 body 的，组件内的 scoped 样式够不到它内部。**
   改它们的内边距、布局，要在组件里单开一个**不带 scoped** 的 `<style>` 块、用 class
   前缀限定住作用域；**只有跨组件共用的才上全局** `frontend/src/styles.css`
   （`.dot` 系列就是这样上去的，它是弹窗与调试抽屉共用的）。
   **`:deep()` 也救不回来**（整理源抽屉三栏布局的实测）：`:deep(.el-drawer__body)`
   编译出 `.tidy-drawer[data-v-x] .el-drawer__body`，而那个带 `tidy-drawer` class 的
   元素**身上没有任何 `data-v-*`**——el-drawer 的根是 Teleport，父组件的 scope id
   落不到里面真正带 class 的元素上，前缀就永远匹配不上。**分界不在「抽屉内外」，
   而在「谁写的」**：我们自己写进抽屉的元素（插槽内容，如 `.row`）照常带 scope id、
   scoped 样式对它们有效；够不到的只有**组件自己的内部结构**（`.el-drawer__body` 等）。
   症状同样是「代码写了、build 过了、界面没变」——那次抽屉退化成整个 body 一个
   滚动条（列表撑到 1.4 万 px，步骤条与底部按钮全被滚出视野），computed `display`
   仍是 `block`。
3. **scoped 规则与全局规则特异性相同时，胜负取决于注入顺序。**
   `.source-tabs[data-v-x]`（0,2,0）与 `.edit-dialog .source-tabs`（0,2,0）同级，
   想稳定覆盖就**多带一级选择器**拿到 0,3,0。
4. **Vue 模板里直接写引擎字面量（`{{ }}`、`<js>`）会被解析掉**——前者当插值、
   后者当标签，而且**转义成 HTML 实体也救不回来**（编译发生在实体解码之后）。
   要原样显示这类清单，用 `v-pre` 让整段跳过编译。

## 十四、App 调试的 tag 是「去 App 库里查」，不是「告诉它跑哪个源」

**症状**：新建的源、或改了规则还没导进 App 的源，点「连 App 调试」什么都不发生，
等满超时才失败；已导入的源却正常。同一个按钮两种结果，失败时还没有任何提示。

**根因**：调试 WS 收到 `{"tag", "key"}` 后执行的是
`appDb.bookSourceDao.getBookSource(tag)?.let { startDebug(...) }`
（`BookSourceDebugWebSocket.kt:39`），而那条查询是
`select * from book_sources where bookSourceUrl = :key`——**精确字符串匹配**。
查不到就什么都不做：不发消息、不报错、不关闭连接。

推论有两条，都不是「用错 API」而是用法本身的前提：
- **新源没法用 App 验证**，除非先把它导入 App
- **规范化过的 URL 一定失败**（正是 core/loader.py 那 20.7% 差异的后果）

**结论**：App 的 Web 服务不只开调试 WS，还开着一组 HTTP 接口
（`KtorServer.kt:57,121`，端口 = WS 端口 - 1）。其中
`POST /saveBookSource`（body 是单个书源裸 JSON；App 侧 `insert` 是 **REPLACE**，
幂等）与 `GET /getBookSource?url=` 正好补上这个缺口：

- 调试前先查一次 → 把「静默无响应」变成 `unreachable / missing / ready` 三态
- 缺源就推一次 → 把当前表单（含未保存改动）发过去再调试，省掉
  「保存 → 导出 → 扫码 → App 导入 → 才能调试」的整圈往返

**代价要讲清楚**：推送会改动用户 App 里的书源数据（同 URL 覆盖）。边界是
**只能在用户主动发起调试、且明确确认之后**、由预检结论决定要不要推——不得有
后台的、没人触发或没问过用户的推送。**「调试」和「往 App 里写」是两件事**：
把推送做成点「调试」的隐式副作用，用户点的是调试、App 里的数据却被改了，而这在
界面上完全看不出来（这一版最初就是这么写的，是用户指出来的）。做成「一个按钮 +
只在需要推送时弹一次确认」，比摆两个按钮好——用户不必先判断自己属于哪一种。
接口细节写在 `core/app_debug.py` 的「HTTP 接口」一节，不要在这里抄第二份。

**只判断「源在不在」还不够**——会漏掉「**App 里有，但是旧版本**」：调试跑的始终是
App 里那份，于是结果看着正常、答的却不是你在改的东西（本类工具最容易骗到人的地方）。
所以预检要**比对规则**，分成 `missing / stale / ready` 三档。

比对有个坑：**别用 `loader.fingerprint()`**——它把整个 `ruleSearch`/`ruleToc`/
`ruleContent` 字典都算进哈希，而 App 存的是它自己的实体（Gson 会丢掉我们多给的键、
补上它自己的默认值），字段集合本就不同，拿指纹比必然每次判「不同」，白覆盖一遍。
**只比调试真正会跑到的、双方都一定有的那几个字符串字段**（清单在 `core/app_debug.py`）。

**顺带**：`run_app_debug` 的返回体一直带 `events`（App 推的原始事件流，含耗时），
前端却从没渲染——**「后端返回了、前端从来不消费」也是一种静默失效**。

## 十五、concurrentRate 是 String 不是 int，而且我们曾经把它抹成 0

**症状**：源自己声明了 `concurrentRate`（就是「这么打我你会被封」），我们不但不遵守，
还在导入/保存时把它**静默抹成 0**——0 在 App 里等于「不限速」。

**根因**：`core/sanitize.py` 把它列进了 int 字段清单，于是 `"1/2"` 走
`int(float("1/2"))` 抛异常、被兜底成 `0`。而这个字段在 Legado 里是
**`String?`**（`BaseSource.kt:35`），两种写法都合法（`ConcurrentRateLimiter.kt:82`
的注释：「并发控制为 次数/毫秒，非并发实际为 1/毫秒」）：

    "n/m"   n 次 / m 毫秒
    纯数字 x  1 次 / x 毫秒

这类破坏**会把自己的证据一起抹掉**——库里存量的 `"1/2"` 早就变成 0 了，事后无法反推
到底破坏了多少条。当时的 3861 个源里 `"n/m"` 写法是 0 个，但那不代表没发生过。

**结论**：三条一起修，缺一不可：

1. `sanitize` 只把纯数字归一成 int，**非数字串原样保留**（`"1/2"` 是合法值，别碰）
2. `checker._request` 发请求前按源声明的间隔等一下（异步 `_throttle`）。源内请求本来
   就是顺序的，不需要锁
3. **`core/fetch.py` 也要限速**（同步 `_throttle` + 模块级状态 + `threading.Lock`）。
   四条抓取链路里只有 checker 走 aiohttp，其余三条——全链路试跑、连 App 调试补抓页面、
   快速新增源——都走这里。漏掉它的后果不是"少遵守一点"：`repair_many` 是自动批量的
   （`Semaphore(4)` + `gather`，默认 3 轮 × 每轮最多 3 次抓取 = 单源最多 9 次），
   而修复的目标恰恰是失效源。**只给 checker 加限速 = 批量校验守规矩、AI 修复连打九下。**

解析口径（`rate_interval_ms`）放在 `core/quality.py`，两边共用同一份——`fetch` 不该
反向依赖 `checker`（§十）。解析不了就不限速：宁可多打几个请求，也不瞎猜一个间隔把
正常源拖慢。

**`"n/m"` 是有意近似**：App 是窗口/突发语义（n 次可以连着发完再等），我们折算成均匀
间隔，总速率一致、突发形状不同（更严格）。别当成"和 App 一模一样"来依赖。

**已知未覆盖**：`fetch._throttle` 的锁只做了逻辑正确性，没写并发用例（那种用例容易
抖动）。去掉锁或把 sleep 挪进锁里，现有测试都不会红。

**顺带一条测试基础设施的坑**：曾经有个测试往 `sys.modules` 里塞空壳 `aiohttp`
顶掉真依赖（理由站不住——aiohttp 是硬依赖），它坑了两次：单跑没事、全量 `discover`
时在 `except aiohttp.XxxError` 求值处抛 `AttributeError`。桩后来删了，但教训留下：
**往 `sys.modules` 塞东西是全局副作用**，测试里做这件事要想清楚影响面。

## 十六、校验「请求成功但状态不变」——三处错凑在一起

**症状**：界面点校验，任务跑完、提示成功，列表里的健康度/星级纹丝不动。
而且有效期内的缓存好像也从来没被复用过。

**根因**：三处，各自都能独立成立，凑在一起才让现象这么难猜。

1. **`run()` 里保存那一段被 `if self.cache_dir:` 挡住**。Web 那条链路
   （`backend/api/ops.py`）构造 AsyncChecker 时传的是 `use_store=True`、
   **不传 cache_dir**，于是整段保存被跳过——算完就丢。
2. **`save_cache_append` 又是先 `os.makedirs(self.cache_dir)` 再判 `use_store`**，
   cache_dir 为 None 时第一步就抛 TypeError。所以就算过了第 1 关也会崩。
   两处是同一个故障的两半，**只修一处仍然坏**。
3. **缓存的键两侧口径不一致**：`Store.save_checks` 存的是**规范化**后的 URL
   （`checks.source_url`），而 `run()` 拿 `record.url`（抓取时的**原文**）去查——
   尾斜杠一类的差异就查不到。这不是「少命中一点」，是**store 后端永远命不中**
   （这个差异本项目实测 20.7%）。就是 §五 那条「跨表/跨库关联的 URL 两侧必须用
   同一套规范化」，只是方向反过来：那次是写侧没归一，这次是读侧。

**结论**：三条都修了，并且都补了离线用例（`tests/test_checker_persist.py`）。
另有两条顺带：

- **写缓存失败不能 `except Exception: pass`**。写不进去的表现是「校验跑了但状态
  不变」，和「源本来就没变」在界面上**完全无法区分**。现在计数 + 收尾打印
  （`save_failures`），任务结果里也带出去。
- **「复用了几条」要报出来**（`cached_count`）。不说的话，「点校验 → 完成」和
  「一条请求都没发」长得一模一样——用户会以为校验过了，其实只是读了缓存。

**推论**：一道门的条件写错（`cache_dir` vs `use_store`），表现可以完全不像「保存
失败」，而像「这个功能本来就不生效」。凡是「A 生效了但 B 没变」的问题，先怀疑
**从 A 到 B 之间那道条件判断**，而不是 A 本身。

## 十七、合并配置时 `None` 是「没传」，`False`/`0`/`""` 不是

**症状**：校验参数支持了「全局默认 + 本次覆盖」之后，用户明确把某个开关关掉
（当时是 `probe_search`，现已并入探测深度；同理 `verify_ssl`）、或明确把代理清空成
直连，结果**参数看起来没生效**——校验还是照常探测搜索、还是走了代理。
界面上没有任何异常，日志里也没有。

**根因**：合并写成了 `payload.get(key) or 全局值`。`or` 对 `False` / `0` / `""`
一律当成「没传」，于是这三种覆盖被**静默吃掉**，回落到全局值。

判据必须是 `is not None`：`False`（关掉证书校验）、`""`（本次直连）、`0`
都是**有意义的值**，只有 `None` 才表示「没传」。
（见 `core/settings_store.resolve_check`；`tests/test_settings_store.py` 里
「keeps_false_and_empty_string」与「none_means_fall_back_to_global」**必须成对存在**——
单独任何一条都拦不住把两者互换的写法。）

**推论**：凡是「默认值 + 覆盖」的合并，先问清楚**用什么表示『没传』**，然后让
它和「传了个空值」在代码里长得不一样。`or` 是最容易把这两件事混起来的写法。

## 十八、判定输入里不能放「我们自己写进去的结论」

**症状**：`reclassify` 的类型判定与源的实际类型系统性不符，漫画站被判成小说；
而且**改不动**——`--write` 改对一批，下次再跑又变回去。看症状像 §四
「类型必须实测，不能信声明值」，但把声明值全清掉，判定照样偏小说。

**根因**：`reclassify._text_of()` 把 `bookSourceGroup` 整串当特征文本读，而这个
group 是 `organizer.group_title` / `store._system_group_for` **按 `bookSourceType`
生成**的，形如 `📖小说,待验证`。于是形成闭环：

    类型错(默认 0) → group 写成「📖小说」 → 命中文本特征 "小说" → novel +3
                  → 单独就到阈值 3 → 再判成小说   ↺

错的标签**自我固化**，永远纠正不过来。实测：命中 "小说" 的 3540 条源里，
**3506 条的 group 带着系统类型标签**（字段分布上 group 单独占 2290 条）；
剥掉系统标签后 **119 条改判**——58 条 `小说→-1`、32 条 `小说→漫画`，
外加 20 条 `漫画→-1`，**循环在反方向同样成立**。

**结论**：判定输入里只能放**原始观测**，不能放「我们自己写进去的结论」。
`_text_of` 现在只取 group 里的**用户标签**（`core/tags.py:extract_user_tags_from_group`）
——那是人主动打的，是真信号；系统标签是派生物，一律丢掉。

> 注意这里是「症状对、归因错」的典型：原判断说的是「`NOVEL_TEXT_HINTS` 含
> `阅读`/`txt` 这类泛词，中文小说站几乎必中」，而实测这三个词各自只影响 **4~5 条**。
> **归因必须靠数，不能靠像**——症状指对了方向，不等于指对了原因。

**推论**：凡是出现「A 的输出被写回 A 的输入」，先问这个字段是**原始数据**还是
**我们的结论**。归档 / 整理 / 标注类功能最容易造这种环——分组、缓存、指纹、
报表、质量标签全是候选。判据要经得起「把派生字段全清掉，结论还成立吗」。

→ 已提炼为 AGENTS #11

**变异要成对**：这次的两条变异 `M6 还原循环`（三条循环用例红）与
`M7 把 group 整个丢掉`（反向断言 `test_user_tags_still_count` 红）是一对。
只做 M6 会让人以为「全丢」也行——**修过头的方向也得有一条断言拦着**。

## 十九、读一个不存在的字段 = 死代码，而它看起来像信号

**症状**：`infer_type_static` 里有一条「有 `ruleContent.image` 图片规则 → 漫画 +3」
的信号，权重高得足以单独定案。它**从未执行过**。更麻烦的是，测试里有一条断言
把这个不存在的信号钉死了，读起来像「这个信号是有效的，只是权重值得商榷」。

**根因**：`ruleContent.image` 在 Legado 的 `ContentRule` 里**不存在**——图片走
`content` 规则本身（`looks_like_image_rule` 判的就是它）。本项目也从不写它：
实测库里的 **3861 条源，该字段非空的是 0 条**。于是 `image_rule.strip()` 恒为假，
`if image_rule.strip(): manga += 3` 是死代码，`:112` 那个
`and not image_rule.strip()` 也永远是 `True`。

危险**不在算错**（它算不出错，因为它根本不算），而在于**它读起来像一个存在的信号**：
有人会照它去调权重，或者以为「图片源有救了」。

**结论**：删掉，并在原处留一行说明**为什么删**，避免被重新引入。删的同时必须
处理那条钉死旧行为的断言——它会把死代码伪装成活的。这次是
`test_image_rule_worth_three` → `test_rule_content_image_is_not_a_signal`
（改成的断言是「带这个字段的源必须和不带时判得一样」）。

→ 已提炼为 AGENTS #12

**推论**：判断一段代码死没死，**别靠读，去数**。这次是一行搞定的：

    sum(1 for s in d if str((s.get("ruleContent") or {}).get("image") or "").strip())

结果是 0，读半小时代码也不会比这更确定。同类可疑字段（本项目还有
`ruleContent.webView`、`bookSourceType == 4`）都该这么过一遍再决定动不动。

## 二十、文档会自己腐烂：一处写，别处只留指针

**症状**：`TODO.md` 在两周里被反复订正——同一个条目的状态改了三次，
每次都要**重新核对代码**才知道它到底做没做。有一份设计文档记的是「已做完」的事，
把它当待办看就会白做一遍。

**根因**：那份文件同时装了两类**寿命完全不同**的东西：

| 类型 | 例子 | 寿命 |
|---|---|---|
| **待办** | 「末段语义要修」「试跑要带 cookie」 | **做完就该删** |
| **知识** | group 循环的机制、`getElements` 与 `getStringList` 的区别 | **要长期留** |

待办混进知识库会**立刻过期**（做完的条目还留着，下次翻到以为没做）；
知识混进待办清单会**跟着被删掉**。所以「怎么订正都还是不对」——
不是写得不认真，是**它的定位本身在漂**。

**结论**：文档按**性质**分层，不按重要程度（重要程度只决定要不要收）。
判据写进了 `AGENTS.md` 硬性约定 #10：约束进 AGENTS、论证进 lessons、
用法进 README/WORKFLOW、待办进 `TODO.md`。**一处写，别处只留指针。**

**推论：待办要按「现在还能触发吗」过，不是按时间过。**

「试跑不带 cookie」这条在写的时候是真的——那时编辑弹窗还有本地离线试跑。
后来那个入口撤了（调试只剩「连 App」，cookie 由 App 自己的 CookieJar 管），
**这条的前提就没了**，而条目在清单上又留了很久，看着像一件该做的事
（直到 2026-09-17 才重写成它真正的样子——「修复循环撞登录墙」，见 `TODO.md` 第 1 条）。

**能力撤了、条目还在**，是待办清单特有的腐烂方式——按时间排序看不出来，
按「现在还能触发吗」一问就问出来。

→ 已提炼为 AGENTS #10（文档也只有一个事实来源）

## 二十一、测试要防的是「形状」，不是「这一条」

**症状**：给 `checks` 表加 `star_basis`，四处（DDL / `NEW_COLUMNS` / `save_checks`
的 INSERT / `checks_map`）都得改。补了「往返测试」和「列名对得上」两条断言，看着很稳——
而**造变异时我自己漏改了 `NEW_COLUMNS`，整个测试文件仍然全绿**。

**根因**：那两条断言用的都是**全新的库**：DDL 直接把列建出来，**根本走不到
`NEW_COLUMNS` 那条路径**。而真实用户的库是旧 schema，补齐靠的正是它。

同类：迁移测试的 fixture 一开始随手编了个「最小表」（只 7 列），结果视图建不起来
（引用了 `probe_depth`）。**那些列本来就不该在 `NEW_COLUMNS` 里——它们是老版本就有的。**
判据是「哪些列是后来补的」，不是「哪些列我懒得写」。

**结论**：

- 加一个跨层字段时，**结构性断言要覆盖两条路径**：新建的库 + 从旧 schema 迁移的库
- fixture 要构造**真正的老状态**（「现在的 DDL 减去 `NEW_COLUMNS`」），不是最小可用集
- 更好的做法是写**结构性断言**而不是逐列断言：「`save_checks` 写入的每一列表里都必须有」
  （正向）+「表里每一列都必须被写过」（反向，排除自增 id）。逐列补只能防住**已经踩过**
  的那些，而这类事情的形状永远是同一个——**加了一个字段，忘了在其中一处落库**。

**推论**：与 §十二 是同一课——**测试的价值在于它拦住了什么，不在于它写了多少**。

## 二十二、归因必须靠数，不能靠像

**症状**：`reclassify` 的类型判定系统性偏「小说」，漫画站被判成小说。
原判断写的原因是「`NOVEL_TEXT_HINTS` 含 `阅读`/`txt` 这类泛词，中文小说站几乎必中」。

**根因**：那个归因**是猜的**。实测逐词移除后的改判数：`xs` 5 条、`阅读` 4 条、
`txt` 1 条——三个目标词加起来 **10 条**。而真凶是 **`小说` 一个词影响 143 条**，
且它不是「泛词」，是**分组标签的自固化循环**（见 §十八）。

**结论**：**症状指对了方向，不等于指对了原因。** 归因要落到可测量的东西上：

    # 一行就能证伪一个猜测
    sum(1 for s in d if ...)

**推论：注释与代码不一致时，信代码。** 当时 `_classify` 的注释写着「其他 2xx/3xx 视为可达」，
而代码是 `return Health.OK`——**没有范围判断**，404 / 400 / 410 / 451 全被判成「可用」
（实测库里 91 条 `ok` + 4xx）。注释描述的是**意图**，代码描述的是**行为**；
两者矛盾时，坏掉的是行为，修的时候两边都要改。

> **该缺陷已修**（`CACHE_VERSION 9`：4xx 一律判 `dead`，见 `checker.classify_http_status`）。
> 留在这里的是**判据**，不是待办：**别把「注释这么写的」当成「代码这么做」。**

## 二十三、同一件事可能走两个函数

**症状**：`class.chapter-list@tag.a` 这类规则，我按源码推断「末段会被当属性名 → 取空」，
于是判定我们的解析器**误放**，还估了 3441 条的规模。而在 App 里实测，
**它能出章节**——结论被当场推翻。

**根因**：**读错了函数。** Legado 对两类规则走的是两条不同的路径：

| 规则种类 | 走哪个函数 | 末段怎么解释 |
|---|---|---|
| 列表（`chapterList` / `bookList`） | `getElements`（`BookChapterList.kt:203`） | **每个 @ 段都是选择器** |
| 取值（`content` / `intro` / `author`…） | `getStringList` → `getResultList` → `getResultLast` | `when` 只认 text/textNodes/ownText/html/all，**其余当属性名** |

所以「末段是动作」只对**取值类**成立、对列表类不成立——两件事都对，不矛盾。
影响面也从 3441 条缩到 **290 条**（只有取值类字段）。

**结论**：**「实测推翻了源码结论」时，先确认两边说的是不是同一条代码路径。**
反例和结论如果走的是不同的函数，那个反例什么也证明不了。

**补充（本次评审）**：这条差异还有一个入口没被覆盖——**HTML 标签名与属性名冲突**。
`title` 同时在 `COMMON_ATTRS` 和 `HTML_TAGS` 里，而 `_looks_like_attr` 先判
`_is_selector_like`，于是 `tag.a@title` 被当成「在 a 里再选 `<title>`」，当前取不到
`title` 属性；按 Legado 的取值语义，`title` 不在 `VALUE_ACTIONS` 里，应当按属性名取。
所以「取值规则末段不是动作就按属性名」这条，不只覆盖 `id.content` 一类，`@title`
也在同一根因里。

**实现约束**：`extract_all_nodes` / `extract_all` 同时被列表规则和取值规则调用
（`checker._confirm_hit` 跑 `bookList`，checker 的 `chapterList` / `content`，
verify 的 search / toc / content 也共用一份），所以在底层改「末段一律按属性名」
会打坏列表规则（`getElements` 要求每段都是选择器）。必须给解析入口加**显式的
list / value mode**，由调用方声明，不能用字段名或启发式猜。

### 第二次实证：同一个「目录验证」也有两份实现（2026-09-19，S3-1 实测发现）

**症状**：JVM 目录段对 100 条抽样给出的 `toc_complete` 与本地 `checks` 里的值
矛盾率 74.7%（远超验收线），方向一边倒：JVM 报 904/1201/438 章，本地报「解析结果为空」。

**根因**：本地**有两处目录验证**，`ruleBookInfo.tocUrl` 只有一处处理了：

| 实现 | 谁在用 | tocUrl 处理 |
|---|---|---|
| `core/verify.py`（试跑/修复循环） | 调试抽屉、AI 修复、快速新增 | ✅ 在详情页上求值（`BookInfo.kt:163` 口径），求值不了判 **unknown** |
| `core/checker.py` 的 `_probe_toc`（写 `checks` 的那条） | **全量校验** | ❌ 直接拿详情页数章节 → 目录在独立页上的源一律「解析结果为空」→ `toc_complete=False` |

而库里**1617 条源**的目录在独立页上——于是这批源在 `checks` 里长期带着一个
**假结论**（不是 unknown，是 False＝"源坏了"）。实测 SF轻小说：本地判 False/0 章，
JVM 报 1201 章；我手工把它的目录页喂给本地回放器，**跑出 1227 个值**——说明
规则本地能解析，**是取错了页面**。

**结论**：同一件事（目录验证）有两份实现时，**修一处必须同时看另一处**；
判定口径的修复要问「这条链路上还有谁在做同一个判定」，否则修好的只是少数入口
（试跑对了、全量校验还错着）。这与 S1 修的 `tocUrl 进探针` 是同一个洞的第二层——
当时只改了 verify 那条链，`_probe_toc` 漏了。

**验收方法论的教训**（比上面这条更普适）：拿两套测量比矛盾率之前，先问**它们是不是
同一把尺**。这次抽样里三类混在一起，看起来是个 74.7% 的大数字，拆开只有第三类是
真问题：

| 类 | 例 | 该不该算矛盾 |
|---|---|---|
| **口径差异** | 本地按参考表比比例（1033 < 1681×0.8），JVM 只有绝对下限 | ❌ 不是矛盾，两把尺 |
| **能力边界** | 本地跑不了某种写法 → 应判 unknown | ❌ 不是矛盾，是本地的边界 |
| **实现缺陷** | 上面那个 tocUrl 漏接（本地宣称能跑、也跑了、但取错页面） | ✅ 真矛盾，且指错方向 |

### 第三次：列表字段的**作用域**（2026-09-19，修 tocUrl 时顺藤摸到）

修完 tocUrl 再测，三条真实源仍然失败——查下去发现**更早一步就错了**：`bookUrl`
被作用于**整页**，于是 `tag.a.0@href` 先命中导航栏的第一条链接，详情页变成站点
首页（`http://www.liudatxt.la/`），后面目录/正文自然全错。Legado 的语义是
**字段在列表节点内求值**（`BookChapterList.kt`：`elements.forEachIndexed {
setContent(item) … }`），`chapterUrl` 同理。

修法：`replayer.extract_field_in_nodes(content, 容器规则, 字段规则, …)`——
一个实现，`checker`（写 checks 的全量校验）与 `verify.py`（试跑链路）都调它。
实测收益：溜达小说 0→1914 章、穿越小说 0→1664、必去网站 0→1491。

**顺带一条更重要的教训：fixture 会编码错误的语义，于是测试是"假绿"。**
这次改动让 9 个既有用例变红，逐一看下来**没有一个是产品回归**，全是 fixture
把旧的错误行为写成了前提——比如 `chapterList: class.chapters@tag.a` 配
`<div class="chapters"><a>`：**列表规则已经选到 `<a>`，字段规则又写
`tag.a@href`**，等于"在 a 里找 a"。App 在这条源上同样取不到 url，只有"对整页
求值"的旧实现才跑得通。**测试通过不等于语义正确——它只说明代码与 fixture 一致**；
fixture 跟错语义时，绿是假的，而且它会在修对的那一刻集体变红，看起来像"你改坏了"。

判据：改语义时若一批用例集体变红，先问**它们的 fixture 是不是照着旧行为写的**，
别急着回滚。

## 二十四、流只是加速手段，真相要在可查询的地方

**症状**：点「全量校验」后界面卡在「正在校验 1 条」，校验按钮永远点不了，只能刷新页面。
（另：一次 3 分 47 秒的全量校验，界面上**全程显示 0**。）

**根因**：两处，各自独立：

1. `subscribeJob` 的 `es.onerror = () => es.close()`——**那一句把 `EventSource`
   自带的重连关掉了**。而服务端本来就是按「状态」设计的（每次连接的第一帧就推当前
   全量），**重连一次就等于补齐终态**。关掉重连之后，一次网络抖动就永久失联，
   而调用方的 `checking` 挂在流的终态上，于是永远不复位。
2. `run()` 里的进度**只 `print` 到控制台**，从不写进 `jobs.progress`；
   结果也是**全部跑完才落库**。于是长任务在界面上没有任何中间态。

**结论**：**只要「UI 状态对不对」依赖于「某条消息一定送到了」，就一定有卡死的窗口。**
这不是 SSE 的缺陷，是**把一次性事件当状态用**的缺陷。

做法：`onerror` 不立即关闭（让它按默认节奏重连）+ **重试上限** + **上限到了也必须
复位调用方的状态**。最后一条才是真正防卡的出口——无论发生什么，它都得有出路。
长任务的进度要写进**可查询的地方**（`jobs.progress`），不能只打印。

一条到底是「还没轮到」还是「已经否决」。见 §二十。

## 二十七、空闲连接池没有上限，而 Windows 的 select() 有 512

**症状**：全量校验跑到一半，整个后端进程带着 traceback 死掉，最后一行是
`ValueError: too many file descriptors in select()`（栈顶是 `asyncio/selectors.py`）。
日志停在哪一条是随机的——本次是「进度: 500/3861」。

**根因**：两件事凑在一起，单看每一件都正常。

1. **aiohttp 的 `limit` 只管「在飞」的连接。** `_release` 之后连接会留在
   `connector._conns` 里等复用（默认 keepalive 15s 才回收），而**那份池子没有任何
   总量上限**（`aiohttp/connector.py` 的 `_release` 与 `_cleanup`）。校验扫的是
   2562 个不同主机（库里 3861 条源），每条源一个连接，池子于是随进度单调上涨——
   实测 20 并发跑 200 个主机，池里躺着 **182 个空闲连接**、事件循环注册了
   **199 个 socket**，远超并发上限 20。
2. **`--reload` 起的后端跑的是 SelectorEventLoop。** uvicorn 只在**非**子进程时
   才给 Windows 上 Proactor（`uvicorn/loops/asyncio.py:9-11`），而 reload 走的是
   multiprocessing 子进程（`Process SpawnProcess-1`）。Windows 的 `select()` 上限是
   **512 个 fd**，一超就抛异常并**带走整个进程**——崩在 500 条正是池子堆到 512 的
   那一刻。

**结论**：多主机扫描一律 `force_close=True`（`core/checker.py` 的 `run()`、
`core/reclassify.py` 的 `_diagnose_all`）。跨源复用本来就少（65% 的主机只有一条源，
最多的 11 条），丢掉的只是同一源内部几个请求（域名→搜索→详情→章节）之间的复用，
换来的是「同时打开的 socket 数**恒定不超过并发上限**」这个硬保证。

**复现方式**（几行就够，别靠猜）：本地起 N 个端口的 HTTP 服务，用 `TCPConnector`
的同一套参数跑 N 个不同端口的请求，打印 `len(loop._selector.get_map())`——修复前
它随请求数线性上涨，修复后贴住 `limit`。

**推论**：
- **`limit` ≠「同时打开的连接数」**，它是「在飞」。凡是「连接数超标」的排查，都要
  看池子里**空闲**的那部分，而不是那个参数本身。
- 报错落在 `asyncio/selectors.py` **不代表是 asyncio 的问题**。先问「谁把 fd 堆到了
  512」，再问「为什么不回收」。
- 同一份代码在 `--reload` 与不带 `--reload` 下跑的是**两个事件循环**，只在其中一个
  上崩是正常的。这类环境差异要有意识地想到——尤其当「明明是同一份代码」。

## 二十八、副作用留在库里，就要有人收尾（判据用进程边界，别用超时）

**症状**：进程崩溃/被强杀之后，任务抽屉里那条任务**永远显示在跑**、「任务」按钮的
徽标也一直挂着。实测：一条 check 停在 500/3861 不动，重启服务也不会变。

**根因**：任务活在**进程内**的 asyncio task 里（`backend/jobs/runner.py` 的
`TASKS`），进程一死它们就没了——但库里那行还写着 `running`，而写终态的那段代码
（`_run` 的 `except`）根本没机会跑。`sweep_jobs` 的 TTL 最终能清掉它，要等 7 天
（那条注释管这叫**僵尸行**）。

**结论**：服务进程启动时把非终态任务收尾（`Store.fail_orphan_jobs` +
`runner.recover_orphans`，由 app 的 lifespan 调）。

**判据只能用「进程启动」，不能用 `updated_at` 超时**：进程活着但卡在一个慢源上
（超时 8s × 最多 5 个请求）和进程死了长得一模一样，阈值只能拍脑袋，还得再养一个
后台清扫任务。而「本进程启动时，库里任何非终态任务都是孤儿」是**确定性**的——
没有假阳性。

**调用点的三个候选只有 lifespan 对**，中间那个是最容易写错的：

| 位置 | 后果 |
|---|---|
| 模块级 import（`app.py` 顶部） | 测试与 CLI 顺手 import 一下就写库 |
| `backend/__main__.py:main()` | `--reload` 下它跑在**监督进程**里。改一行代码热重载 → 子进程重启，而监督进程没重启 → 清理不执行。**恰好漏掉最常发生的那种情况** |
| FastAPI 的 `lifespan` | 跑在服务进程里，每次启动/重启都执行一次 ✔ |

**推论**：
- 凡是「进程内状态 + 落库状态」两份的东西（任务、锁、租约），进程一死两边就分叉，
  必须有人按**进程边界**对账。判据能确定性就不要用超时——超时是需要拍数的猜测。
- 启动钩子的位置是**逻辑的一部分**，不是风格问题。有 supervisor 的部署方式
  （`--reload`、多 worker）时，先问「这段代码到底跑在哪个进程里」。
- 同类问题还有一种是**只增不减的表**：`jobs`/`exports` 都有 TTL 清理，`checks`
  一条都没有，而它的**全部读者都只取每源最新一条**——历史行没有任何读者，却攒到
  6626 行 / 26.6 MB 才被发现（瞬时网络结论落库之后更是每次全量稳定 +1000 行）。
  判据：**每张只有 INSERT、没有 DELETE 的表，都要能回答"谁删"**；答不上来就是
  在等它长到有人注意为止。保留策略要和「读取口径」对齐（这里必须留
  `checks_map` 会返回的那一条，否则清掉的正是界面上显示的那条）。

## 三十、DNS 判死必须两个独立来源同意

**症状**：域名探测报 DNS 失败时，`DEAD`（该删）和 `GFW`（该翻墙）长得一模一样。
原来的处理是一律按「待复检」，理由是"无法区分"——保守，但用户拿不到任何可操作的
结论，而这类源在库里是成批的（1222 条里约一半是 DNS 失败）。

**根因**：只有**本机视角**。本机解析失败可能是域名注销，也可能是 DNS 被污染
（或被墙），一次解析失败分不出来。

**结论**：补一个**外部视角**（`core/dns_check`），向两个公共解析器直查 A 记录——
**直发 IP（UDP/53），不能走系统解析**（要查的恰恰是"系统解析为什么失败"）：

    任一给出 A 记录      → polluted → 该翻墙（域名存在，是本机解析不到）
    两个都回 NXDOMAIN    → gone     → 该删
    其余                 → unknown  → 维持「待复检」

**判死必须两个独立来源都同意**：境内解析器对封锁域名常常直接回 NXDOMAIN（那是
策略应答，不是"域名不存在"）——只凭它就会把"该翻墙"的源判成"该删"，而判死的后果
是**用户去删源**。实测那条边界真的会撞上：`九妖漫画` 的域名阿里说"不存在"、
Cloudflare 连不上，规则把它留在了「待复检」（只凭阿里就已经判死了）。

**推论**：
- 两个方向的错代价**不对称**时，不确定性要往**代价大的那一侧**倒——判死会让人删源，
  判"待复检"只是多跑一次，所以宁可不判。
- 这类"本机视角 vs 外部视角"的判定，同一个模块里还会再遇到（被墙/污染/运营商劫持
  都是这个形状）。做法可以复用：**外部视角 + 多来源一致才下结论 + 说不清就说不清**。
- **同一个判定有第二个入口时，让第二个入口去调第一份实现**，别各写一份。这里是
  CLI 的 `diagnose`（`core/reclassify`）——它原来对任何传输失败都归「死站」并建议
  淘汰，与本条判反：抽样里六成的 DNS 失败是"污染"（该翻墙），照那份报告清理就会
  删掉还能用的源。见 §二十三。

**顺带**（同一轮）：`error` 字段原来对着一整桶失败只写「网络异常」，而抽样 20 条
里它底下混着 4 种成因（连接被拒 / 对端断开 / 证书 / 协议错误）。现在把**底层异常
类名**带出来（`网络异常（ClientOSError）`），并把**证书问题单独一档**
（`Health.CERT`：站点是通的，关掉证书校验就能用——这是这批源里唯一我们自己能处理
的一类，混进「异常」等于把可操作的信息丢掉）。

## 三十一、数字必须带环境，快照不能跨环境比较

**症状**：同一份文档里的两批计数对不上——A 档一个环境是 110 组 / 228 条、另一个是
109 组 / 226 条；星级分布一个环境是 5★ static 314 / 0★ 1503、另一个是
5★ static 212 / 0★ 442。看的人第一反应是「数据过期了」，于是去怀疑代码或缓存；
其实两组数都可以是对的。

**根因**：`data/` 是运行时数据，不进版本库。不同机器、不同库、不同时间跑出来的
快照，源条数、校验结果、标签集合都可能不同。文档里只写数字、不写环境，读的人就会
把两个口径不同的快照放在一起比较。

**结论**：凡是要进文档或决策的计数，必须带四元组：

    环境标识（哪台机器 / 哪个库） | 库路径 | 源条数 | 快照时间

比较只在「同一环境 + 同一口径」下做；跨环境只能比**定义 / 比例 / 方向**，不能比
绝对值。更好的做法是：文档里不写死数字，给一条可复现命令，让读者在自己的环境跑。
「A 环境是 314 条，所以 B 环境也要改 314 条」这种句子，一定是错位。

**口径还包括「判据 / 字段范围」**：同一个库、同一时刻，换个计算口径
（例：重复源的指纹里算不算名称）组数就会变——**数字要带「环境 + 判据」两份**。

**推论**：评审时看到数字对不上，先问「这是不是两个环境」，再问「是不是过期」。
两者都是真问题，但修法不同：环境问题修的是**标注方式**，过期问题修的是**数据**。

## 三十二、外部导入的陌生标签：默认清掉

**症状**：导入一批外部书源后，「标签管理」里冒出一堆没见过的垃圾标签；而代码里
明明有一段「按 known_tags 过滤」的分支。

**根因**：那段分支没有活调用者——`backend/api/imports.py` 传了
`allow_new_tags=True`；`save_source` 又用 `set_user_tags` 整组覆盖。两条写入路径
（导入 vs 手动编辑）共用一个 upsert，契约没定。

**决策**：**默认用户标签 = `R18` / `正版`（`core.tags.DEFAULT_USER_TAGS`）。
外部导入只保留「默认标签 + 库里已有的用户标签」，陌生标签直接清。**
手动编辑（`save_source`，前端 `allow-create`）是用户主动行为，另论——不要把
「导入不污染」收紧成「用户不能新建标签」。

**落地**：

- 白名单唯一出口：`Store.known_user_tags()` = `DEFAULT_USER_TAGS` + 库里已有用户标签；
- `backend/api/imports.py` 在导入边界按它过滤（空库也过滤——默认标签不依赖库内容）；
- `Store.upsert_sources` 里同一份名单是第二道防线；`allow_new_tags=True` 只留给
  seed / migrate 这类整库搬运，不对外部导入开放；
- 空库例外（`count_sources() == 0`）仍保留给 `store_migrate`，但外部导入在入口
  已过滤，不会借它把陌生标签写进去；
- 手动编辑不受限，但代码注释要写清「导入 ≠ 编辑」。

**推论**：同一张表被「导入」和「用户编辑」两条路径写入时，**过滤规则必须按路径定**，
不能塞进共用的底层写入；否则不是导入漏了，就是用户被静默限制。

## 三十三、派生缓存不做向后兼容

**症状**：判定口径一变（逻辑、探测轴、字段含义），旧缓存里的结论就与新逻辑不是一套；
若做兼容，旧 health / star 会混进新报表，表现是「修了等于没修」。

**结论**：缓存是纯派生数据，**口径一变就整体作废**（`CACHE_VERSION` 加一），
不做迁移 / 兼容。代价是一次全量重跑（数量按环境，几千条量级），已知且接受。
旧缓存里的 health 是旧逻辑的产物，混用比全量重跑危险。

**推论**：判断一个字段能不能做兼容，先问它是**原始观测**还是**我们的结论**——
结论类字段（health / stars / tags）不兼容；观测类字段（页面文本、耗时）可以尽量保留。

## 三十四、合并重复源：口径与写路径

**口径**：

- A 档按行为字段比较，**`bookSourceName` 不参与**（改名不等于换源）；
  `core/dups.NON_BEHAVIORAL` 是唯一的排除表。
- 跨域名 A 与 B（同域名）/ C（同名）默认只展示、不预勾选：删掉的是备用入口 / 不同实现，
  不是纯冗余；A/B/C 会大面积重叠，UI 按 A 优先去重。
- 不按域名批量去重；不改地址（地址是 Legado 的源身份，改了在 App 里等于换了一条源）。

**硬边界（2026-09-17 落地）**：可合并 = **同一站点（`site_key`：host + 有效端口）+
行为指纹相同**。`site_key` 把 `http://a.com:80` / `https://a.com:443` / 空端口归一为
`a.com`，但保留非默认端口（`a.com:8080` 与 `a.com` 是两个站点）；scheme 不参与比较。
跨站点的同规则组归只读 `mirror`（`find_mirror_groups`），UI 不提供「加入合并」；
`POST /api/sources/merge` 对**跨站点或规则指纹不同**都直接 400，
不提供 `allow_cross_host` 逃逸口（后端不能信前端的分组）。
理由：域名 / 端口是端点身份，规则相同只说明规则文本一样；App 按 `bookSourceUrl` 认源。

**写路径**（`POST /api/sources/merge`）：

1. 标签取并集，`tags_added` 只装**本次真正新增**的（相对保留条原标签的差集）；
2. 备注默认不合并；勾选时保留条在前、其余按成员顺序、去空与完全重复、`\n\n` 连接、
   上限 4000 字符；
3. **软删除最后执行**，`reason` 写「合并到 <保留地址>」；快照追加到
   `data/backups/deleted.jsonl`，不新增备份机制。

**撤销**：走 `POST /api/sources/merge/undo`（恢复被删条 + 摘真增标签 + 还原备注），
**不要复用 `save_source`**——它会 `set_user_tags(body.user_tags)`，漏传就把保留条标签清空。
撤销入口只活在本次会话（结果条），刷新即失效。

**推论**：合并这种「删除 + 吸收标签 / 备注」的动作，回滚信息必须由写接口原样返回
（哪些标签是真增的、备注改前是什么），不能让调用方自己猜或从最终状态反推。

## 三十五、名称清洗：规则、置信度与缓存代价

**预演只读**：`core/name_clean.py` 是纯函数，`POST /api/sources/names/preview`
只出建议（含原因码的中文表），写路径是 `/names/apply` + `/names/undo`。
（原稿提到的 CLI `clean-names` **没有实现**，别再引它。）

**规则边界**：

- 只改展示名；`source_url` 是身份，绝不改。
- 品牌数字保护：`52书库` / `SF轻小说` / `PO18` 不被去尾部数字误伤；尾部数字只有在
  有 `#` / emoji / 空白 / 括号分隔，或去掉后名字已在库中时才删。
- 类型 / 品牌 emoji（🎧🎨📖📥📚🎵🎬📺🔞）首尾保护；其余装饰符号才清。
- 空 / 过短才回退域名主名，且置信度降到 0.5 以下。

**调试那条链路同理**：调试抽屉跑的是**表单里当前的规则**，源没保存时它的
`fingerprint` 与库里那行不一致，于是那次调试写下的缓存**下次校验用不上**
（`is_cache_item_valid` 要比 fingerprint）。这不是缺陷，是「缓存键就是规则本身」的必然结果。

**写路径的代价**：`core/loader.fingerprint` 包含 `bookSourceName`，改名会让校验缓存
失效、下次重跑。apply 必须同时更新 `sources.name` 与 `raw_json["bookSourceName"]`，
并返回 `old_name` 走专用 `/api/sources/names/undo`；**不要复用 `save_source`**
（会 `set_user_tags` 清标签）。入库链路自动规范化是另一个契约：只对确定性白名单自动应用，
低置信度只给建议。

## 三十六、特征词表里不许放「裸词」——同一个坑栽了第二次

**症状**：大批源被判「需验证」，而它们在 App 里明明能用。实测 1069 条 auth 里
871 条是 `status=200`，其中 797 条带 `cookieJar` —— 它们全是被「登录墙」那条启发式
判出来的。

**根因**：`LOGIN_MARKERS` 里有裸的 `login` / `sign in`。它们匹配的是页面里的登录
**入口**而不是登录墙：实测 `m.cread.com` 的 33KB 首页零反爬词，唯一命中的是
`<a href="/user/login.aspx">` —— 页头一个登录链接。

**这是第二次**：v7 删掉过裸 `cloudflare`（它匹配的是 Cloudflare 的邮箱保护脚本，
站点当 CDN 用就会被注入）。两次形状完全一样：**一个普通英文单词被当成特征词**，
而它在正常页面里到处都是。

**规矩**：特征词表（`ANTI_BOT_MARKERS` / `LOGIN_MARKERS`）里只放两种东西——
中文短语（「请登录」「人机验证」），或**只在那种页面上出现的英文短语**
（`sign in to continue` / `login required`）。放单词之前先问一句：
「正常页面上会不会出现它？」会，就不能放。

**判据还要配「留痕」**：判 `auth` 时把命中的词写进 `record.error`（「页面出现
「请登录」…」）。这条误判之所以查了很久，就是因为当时什么都没记，只能怀疑程序。

## 三十七、列里显示什么，就按什么排

**症状**：按「验证深度」排序，数据看起来完全没排。实测前十行是
`正文 ✓ / 目录 ✗ / 目录 ✗ / 正文 ✗ …`。

**根因**：列里显示的是**结果**（`正文 ✓`），而排序键是**深度**。排序本身没错
（前 30 行全是 depth=4），但 depth=4 里既有通过、有没过、还有只拿到目录结论的，
凭肉眼看就是不有序。**排序键与显示口径必须同源**。

**复合排序键还有两个坑**（这次都踩了）：

1. **方向占位符必须落在主键上**。写成 `"<CASE…>, probe_depth DESC, id" % direction`
   的话，方向会拼到末尾的 tie-breaker 上，主键反而按默认 ASC —— 表现是
   「第一条永远是没验到的那批」，看起来像没排序。
2. **CASE 的优先级必须与列里显示的完全一致**。写成 `content_ok = 1 OR toc_complete = 1`
   时，「目录完整但正文不可用」被算成**通过**，而列里显示「正文 ✗」—— 排序与看到的
   又对不上。显示是「正文优先、其次目录」，CASE 就必须同一个顺序。

**推论**：改一列的显示口径时，顺手检查它的排序/筛选口径。这三处（这次的排序、
健康列、勾选同步）全是同一个毛病：**一屏上两个东西说的不是一回事**。

## 三十八、同一屏上的两个来源，会互相打架

三处实例，症状都是「某个地方显示的东西和它旁边的对不上」：

1. **锁定 vs 实测**：健康列读的是 `checks` 的实测结论，而「锁定健康状态」只改了
   `group_name` 里的标签 → 用户锁了「可用」，列里还显示「失效」。锁定的语义就是
   「以我为准」，所以锁定后列要显示锁定的值，实测值降级进 tooltip。
2. **表格勾选被自己的事件覆盖**：`syncTableSelection()` 用 `toggleRowSelection()` 勾，
   而**它会触发 `selection-change`** → 事件处理又拿「当前表格状态」重算 `selected`
   → 同步过程被自己的事件反过来覆盖。表现：「选中全部 N 条」后表格一格都不勾、
   翻页回来全丢，而批量条上的数字还停在 N。修法是同步期间置一个标志、让事件处理直接
   return（`clearSelection` 同理）。
3. **排序键 vs 列里显示**（见 §三十七）。

**推论**：同一屏上出现「同一件事的两个数字/两处状态」时，先问一句
「这两个来源是同一次写入吗？」——不是，就得挑一个当权威，另一个降级成补充信息。

## 三十九、SQLite 连接跨线程；建 schema 是进程级的事

两条都是「只在并发下复现、串行永远不复现」的随机 500：

1. **连接跨线程**：FastAPI 的 sync 依赖（`get_store`）与 sync 端点各自向 anyio 线程池
   要线程，**不保证是同一个 worker** → `sqlite3` 默认的 `check_same_thread=True` 抛
   `ProgrammingError`。放开是安全的：本机 `sqlite3.threadsafety == 3`（串行化），
   而且那条连接只服务一个请求。**别把 `check_same_thread=False` 去掉**。
2. **建 schema 被每请求重跑**：`_init_schema` 里有 `DROP VIEW v_sources` + `CREATE VIEW`
   （视图定义要重建才会更新）——每次请求都跑的话，并发下几个连接互相把视图删了再建，
   表现是「view v_sources already exists」与「no such table: v_sources」交替出现。
   建 schema 是**进程级一次**的动作，不是连接级的。
   （那几条 `*_once` 的存量修复也在里面，口径随之变成「每进程首次打开库时跑一次」。）

实测：修前 20 并发出 1 次 500；两层都修完后 240 并发全 200。

## 四十、平台与工具链的坑

**一、Windows 把 `.js` 当成 `text/plain`**（后端托管 `frontend/dist` 之后**整页白屏**，
Linux/macOS 复现不出来）：注册表把 `.js` 关联成 `text/plain`，Python 的 `mimetypes`
会读注册表 → 打包好的 JS 被当纯文本发出去 → `<script type="module">` 对 MIME **严格
校验**，浏览器直接拒绝执行（`.mjs` 反而正常，注册表里没有它）。
**修法**：`mimetypes.add_type("text/javascript", ".js")` 显式钉死，别依赖机器注册表。

**二、`index.html` 必须 `no-store`，`/assets/*` 才长缓存**：Vite 产物名带内容哈希，
重建后旧 index.html 引用的文件已不存在——浏览器拿缓存里的旧页面去要资源就是 404 +
白屏，而「没写响应头」时浏览器对 HTML 的启发式缓存是**默认行为**。

**三、写入时的转义会被"吃掉"成控制字符**：用脚本改文件时，多层引用里的转义序列会
退化成**真的控制字符**落进文件。这次它让三个节点统计正则永远匹配不到，而诊断**错误地**
报「页面里没有这类节点」——看起来像数据问题。**改完用 `repr()` 看一眼落盘的实际字节。**

**四、别用 `git checkout -- <file>` 还原**：那会连**你这轮未提交的改动**一起抹掉
（这次差点把 `CACHE_VERSION` 11 / `cache_ttl_auth` 全链 / 留痕三处全丢）。
变异验证要还原时，用脚本化编辑反向替换，或先把改动提交 / 暂存（见 §十二）。

**五、往文件头附近插代码要先看一眼**：曾把 `from __future__ import annotations` 挤到
非法位置（往 `cli/main.py` 头部插 `sys.path` 引导时）。**插完扫一遍文件头。**

## 四十三、页面缓存：加在一个函数里，但三条边界不能省

**症状**：调试的反馈环是**重新联网**——改一次选择器就要重抓一遍（实测单页 p50 805ms、
搜索/详情/正文一条链 2.4 秒），而解析本身是毫秒级。收益最大的是 AI 修复循环：
证据只抓一次，但**每一轮都重跑 `verify_chain`**（最多 3 轮 = 9 次抓取）。

**做法**：缓存只加在 `core/fetch.py` 的 `fetch_ex()` 里——它是**全仓唯一的同步抓取
出口**（analyzer / App 调试补抓 / verify_chain / AI 修复的证据 / 快速新增源全走它），
所以四条链路自动受益，不必逐个改。`fetch()` 保留原名与签名做薄包装（13 个既有调用点
零改动），`fetch_ex()` 多返回 `Fetched(html, cached, fetched_at)`。

**三条边界**（都是取舍，不是实现细节）：

1. **键必须含请求身份**（URL + 请求头 + charset + 代理），只按 URL 做键会把带登录态
   与不带登录态的页面串在一起（同 §五）。URL 用**编码后**的那份：`?q=我` 与
   `?q=%E6%88%91` 是同一个请求，不该各占一格。
2. **命中缓存必须与重新抓取等价**。所以超上限（1MB）的页面**不缓存**，而不是截断后
   缓存——截断会让解析看到半页 HTML，同一个源两次试跑给出不同判定，而界面上没有
   任何东西说明为什么。只缓存抓成功的（4xx/5xx 由 urllib 抛，走不到写入那一步）。
3. **可见 + 可控**。「你看到的不是我刚抓的」是默认开着缓存的唯一代价，所以：
   `pages[].fetched_at` / `cached` 一路透传到抽屉；调试卡片给三档（用缓存 / 只读缓存
   / 忽略缓存）。**只读那档绝不偷偷联网**，缓存缺失抛 `CacheMiss` 并单独给话术，
   **不与「抓取失败」合流**（同 §二）。

**易混点**：这不是「结论缓存」。checker 走 aiohttp、**不经过 `core.fetch`**，所以
校验结论不受影响，**不需要 `CACHE_VERSION`**（§三十三 那条轴管的是 `checks` 表）。

## 四十四、本地回放的边界要分三类：做不到 / 没实现 / 能做

**症状**：`SF轻小说` 校验报「目录解析结果为空」＝**判源失效**，而 App 调试里能正常抓到
目录与正文。看着像源坏了，其实源是好的。

**根因**：`rule_supported` 只回一个布尔，把**两类完全不同的东西**归成了一类：

| 类别 | 例子 | 该报什么 |
|---|---|---|
| **真做不到** | JS（`@js:`/`<js>`）、`{{}}` 模板、XPath —— 要 Rhino | `unknown`（§二 的灰态） |
| **我们没实现** | `text.` / `children.` 简写、`\|\|` 备选、JSONPath 的 `..`、`&&`/`%%`、区间索引、`$n`、`@get:` | **也是 `unknown`，但现在报了 `fail`** |

第二类里最典型的是简写：`parse_rule("text.点击阅读@href")` 报 **`supported=True`**——
因为 `text.` 不在 `RULE_PREFIXES` 里，于是被当成普通 CSS 选择器走进 `select()` 那一支，
**必然为空**。App 那里它是 `temp.getElementsContainingOwnText(rules[1])`
（`AnalyzeByJSoup.kt:313-320`，同处还有 `class.` / `tag.` / `id.` / `children.`）。

规模：**466 条源（12.3%）**用到这两个简写，且样例几乎全在 `ruleBookInfo.tocUrl`
（`text.查看完整目录@href` / `text.章节目录@href`）——**目录在哪一页，正是用简写表达的**。

**做法**：`parse_rule` 要认全 Legado 的简写；**认不出来的一律报 unsupported**，
不能默认当 CSS。这与 §二 是同一族但方向相反：§二 是「该失败的没失败」，
这里是「该说『不知道』的说了『坏了』」——**把工具的欠缺说成源的问题**。

**2026-09-18 已落地**（每条都带自己的原因——别都归到「选择器无法解析」，那读起来像
用户写错了规则）：`text.` / `children.` 简写、方括号索引式（`[-1]` / `[0]` / `[1,3]`）、
**排除索引**（`li!0` / `dd!0:1:2`）、`//` 开头的 XPath。解析期漏网的非法选择器由
`_css_select` 兜底：先过一遍 `soupsieve.compile`，**判定不依赖「上游有没有命中」**
（只在 `select()` 抛异常时才算的话，节点列表为空就变成 fail 了）。
实测这一改让 **1031 条源（27.3%）**的目录/正文结论从 `fail` 翻成 `unknown`——最大
一块是排除索引 589 条。

**同一个坑还埋着第二层**：修完判定才发现 JSON 的 `$.data.list[0].name` 一直是空值——
`_json_walk` 支持 index 步，但 `_walk_hits` 的通用 index 分支排在它前面，**货到不了**。
**「解析器说支持」不等于「跑得出值」**：判某类写法能不能用，去看 `extract_all_ex` 的
返回，别读代码推断。

**反向约束**：`a[href]` 这类**合法 CSS 属性选择器**（450 条源）一个字都不能动，所以
索引检测只认「括号里全是数字 / `-` / `:` / `,` / `!` / 空格」。

**易混点**：`unknown` 的语义是「我们判不了」，它的存在就是为了**不误杀**。
凡是新增判定分支，都要问一句：**这个分支不知道的时候，会不会被下游当成"源失败"。**

## 四十六、界面文案：说状态和动作，不解释机制

**症状**：调试抽屉「候选规则」那块的说明，被连续否掉两轮，反馈是「看不清楚」「像 AI 写的」。

**根因**：写成了**说明文**——解释机制、用破折号和括号堆从句、用指代、同一个东西两个词：

| 违反的惯例 | 原文 |
|---|---|
| 一句话不超过一行，长内容**断成两句** | 「还没配模型，去…**；**下面那趟不花模型，照样跑」——一个分号塞了两件事 |
| 说状态和动作，不解释机制 | 「先拿 App 实测值对一遍」在解释"谁在跟谁对" |
| 不指代前面的话 | 「下面那趟」——用户得往回读 |
| 同一个东西只用一个词 | 一会儿「模型」一会儿「AI」 |
| 状态用名词短句 | 「哪条候选对」是问句，不是区块标题 |
| 不用内部黑话 | 「程序挑的」→「自动挑的」 |

**做法**：每处压到一行；状态用名词短语，动作用动词；机制放 tooltip 或干脆不写。
技术数字（tokens / 缓存命中）**不口语化**——它的读者就是要看数字的人。

**易混点**：这不是"写得客气一点"，是**信息结构**问题：界面文案回答"现在是什么、
我能做什么"，不回答"为什么这样"。

**术语表的依据：谁先说的算。** 界面总称统一为「调试」——**上游 App 自己就叫调试**
（`strings.xml`：`debug_source`=调试源、`debug`=调试、`debug_finished`=调试结束），
而「试跑」是我们自造的，用户得先猜它和「调试」什么关系。层次用**修饰语**区分、
不另造词：App 那层「连 App 调试 / App 实测」，本地那层「本地调试 · 仅供参考」。
一屏之内四个词指同一件事（回放/重放/试跑/重跑，实测界面层 86 处）是最常见的病
——**用户不是看不懂词，是得先做一次词义对齐**。

**机检：这一节不能只靠自觉。** 文案漂移与枚举漂移是同一类问题（#7/#8/#10 那条
原则的第四次应用），所以规则写成数据放 `tools/check_copy.py`，由
`tests/test_copy.py` 挂进 unittest（AGENTS #18）：

- **提取必须能区分注释与文案**——本仓库中文注释极多，注释里的「回放/口径」是写给
  改代码的人看的，算进去就是满屏误报、工具当场失去信用。同理跳过 `console.*`。
- 三条护栏都是实测踩出来的，不是设想的：模板文本节点**只在 `<template>` 里找**
  （`<script>` 里的 `=>` 会被误认成标签边界，把 `.map((v) => …)` 整段报成文案）；
  **取捕获组算长度**（带上引号会把 35 字报成「长句」）；**子串护栏**（「直接调
  **试跑**的是」里的「试跑」是「调试 + 跑」，不是那个词）。
- 基线**只减不增**：键含文案哈希，改一个字就得重新判断一次；必须逐字保留的串
  （换词表的键，见 AGENTS #17）写行尾 `# copy-ok: 理由`、**不进基线**——基线里
  出现永久条目等于把闸门关掉。
- **盲区要认**：机检只抓表里有的词。同一屏上两个兄弟诊断用词不一致（一处
  「本地调试不了这一步」、另一处「本地复盘」）它抓不到；那类只能靠人读一遍。

→ 已提炼为 AGENTS #18（界面文案）

## 四十七、性能结论必须实测——不要给一个看起来很具体的估算

**症状**：为评估"推送全部源 + 逐条走 App 调试"是否可行，给出
「每条 5–30 秒 × 3774 条 = **5–31 小时**」，据此判定不可行。
用户实测跑过 **3000+ 条批量调试，根本没这么慢**。

**根因**：那条估算**没有任何测量支撑**——是从协议（"每次调试要跑完整链路"）
推出来的想象。而它长得非常具体（给了区间、给了总时长），**会被当成依据**
去否掉一条本来可行的路。同 §三十一「数字口径必须带环境」。

**做法**：性能断言要么带实测（环境 + 样本 + 数字），要么明说"没测过"。
**"我不知道"比一个编出来的区间有用得多**——后者会把讨论带偏一整个回合。

**易混点**：这条和"不要凭印象下结论"是一回事，但触发点更隐蔽：
推理链看着是通的（"调试要跑完整链路"→"每条要几秒"），**只是中间每个数都是编的**。


## 四十八、在 JVM 里跑 App 的规则引擎：可行，坑全在「环境」上

**症状**：想在不依赖设备的前提下用 App 的真实规则引擎校验源。第一反应是"那要么改
App 源码、要么自己复刻引擎"——两个都不必。

**查证**：Robolectric（App 仓库本来就在用，`JsTest` 等测试就是它跑的）能在纯 JVM 里
加载 App 代码。探针：对一条真源调 `WebBook.searchBookAwait`，**真联网返回 8 本书**。
根因很简单：Rhino / OkHttp / Jsoup **全是纯 Java 实现**，本来就跑得起来。

**要补的「依赖尾巴」总共三项**（一路撞出来的，别指望一次跑通）：

1. Koin 未启动（`AnalyzeUrl` 构造期要设置网关）→ 测试里起最小 Koin + 一个桩，
   那个网关是**纯数据类**（UA / 线程数），不是 Android 依赖；
2. `appCtx` 未初始化（`appDb` / `CacheManager` 依赖它）→
   `RuntimeEnvironment.getApplication().injectAsAppCtx()`（splitties 的**公开 API**）；
3. assets 路径用 `File.separator` 拼（Windows 上是 `\`，而 `AssetManager` 只认 `/`）
   → 测试侧 shadow 把路径归一。**这个 shadow 要用 Java 写**：拦的是静态 native 方法
   （`nativeOpenAsset` 等），Kotlin 覆盖不了静态方法（报 `Unresolved reference`）。

**零入侵的挂载方式（关键）**：源码放**我们自己的仓库**，由 init 脚本在构建时挂进
`:app` 的 test 编译——App 仓库 `git status` 恒为空，跟上游同步零冲突。三条硬约束，
**每条都踩过**：

- **不能碰 `android.sourceSets.test.java.srcDir(外部目录)`**：Gradle 的**测试发现会
  整个失效**，连 App 自带的测试都报 `No tests found`。测试识别依赖「类文件 ↔ 源码路径」
  的**相对映射**，源码根一旦跑出项目根，映射就断。要挂就给**编译任务** `.source(dir)`。
- **CWD 必须是仓库根，不能用 `-p`**：同一个根因，`-p` 让 CWD 停在别处同样静默失效。
  症状与上一条一模一样（`No tests found`），**但成因不同**——两条都要查。
- Kotlin 编译任务要**单独** `.source(dir)`：KGP 在本脚本执行前已快照过自己的源码目录，
  追加 android 的 `java.srcDirs` 对它无效。

**工具链的四个坑**：`GRADLE_USER_HOME` 必须与项目**同盘**（否则 KSP 报
`this and base files have different roots`）；sdkmanager 自带下载器**会卡死**
（实测卡在 16MB 不动），curl 手动拉包 + 解压到 `platforms/`/`build-tools/` 更快；
`.bat` **必须全 CRLF**（混 LF 会让 cmd 把行拼错、参数被污染）；
从 git bash 调 `.bat` 时**别给 `--tests` 的值加引号**（MSYS 把 `"` 转义成 `\"` 原样传进去
→ 同样报 `No tests found`；cmd / PowerShell 下没这个问题）。

**结论**：这条路可行且 **App 源码一个文件都不动**。代价集中在「环境」——首次十几分钟
（下 SDK / Gradle / 依赖），**每次增量跑约 15 秒**。

## 四十八点五、Robolectric 跑真代码的启动时序：两类「静态初始化」要先喂饱

**症状**：探针单源跑通后，批量跑真实源库，冒出一批 `error`，其中两条的根因
（挖开 `ExceptionInInitializerError` 的 cause 才看到）都指向**静态初始化**：

| 根因 | 触发者 | 修法 |
|---|---|---|
| `NullPointerException`（AppConst.<clinit>） | `AppConst.sha256Signature` 读 **APK 签名**判断官方包；Robolectric 应用没有签名 | 用 Robolectric 标准 API 装：`ShadowPackageManager().installPackage(带签名的 PackageInfo)`。⚠️ `Signature(String)` **只认 hex**，传普通字符串 shadow 自身会崩；用 `Signature(byte[])` |
| `Unable to load PublicSuffixDatabase.list`（OkHttp 静态块） | `NetworkUtils.getEffectiveTldPlusOne` → okhttp 的 PublicSuffixDatabase 静态初始化要 **applicationContext** | 启动时先 `okhttp3.OkHttp.initialize(appContext)`（报错信息里其实自己写了） |

**方法论**：这两条都是**先用 root cause 链定位、再修**——`ExceptionInInitializerError`
的 `message` 是 null，直接打印会把「环境缺口」和「源的问题」混成一团。结论输出里要带
`root`（cause 链尾）与 `root_stack`（帧），定位成本从「猜」降到「读」。

**另一类坑：Gradle 的 UP-TO-DATE 会吃掉参数**——跑批参数写在属性文件里、由测试任务
读，**必须把该文件声明为任务的 `inputs.file`**；否则改了参数 Gradle 仍判 UP-TO-DATE
静默跳过，你以为跑了、其实什么都没发生（与 §十六「请求成功但状态不变」是同一形状：
动作成功了，效果没发生）。

**传参链**：bash→cmd→gradle 三层引号转义不可靠（实测三层都被坑过）；

## 四十九、WebView 不是一个 API，它是一整个浏览器

**症状**：App 里带 `webView:true` 的源在 JVM 服务里跑不了。直觉会问"Robolectric 不是
能模拟 Android API 吗"。

**根因**：整套栈里 OkHttp / Jsoup / Rhino 都是**纯 Java 实现**，所以规则引擎能整个跑在
JVM 上；唯独 **WebView 是 Android 平台里的一个 Chromium**（4.4 起的内核）。Robolectric
能模拟 **API**，模拟不了**引擎**——它的 `ShadowWebView` 只是**记账**：`loadUrl()` 把 URL
记下来，不联网、不渲染、不执行 JS，`onPageFinished` 也不会自己触发。于是
`BackstageWebView.getStrResponse()` 会**一直等到超时**（默认 60 秒）——不是"返回空"，
是**等一个永远不会到来的页面加载完成**。

**它的真实形状**（读 `BackstageWebView.kt`）：WebView **只替换取数那一步**，不参与规则
求值——接口收口在**一个类、一个方法**。缺省行为一句话：**加载页面 → 执行 JS（默认
`document.documentElement.outerHTML`）→ 把渲染后的 DOM 当响应体返回**，顺带把浏览器
cookie 写回 `CookieStore`。所以"要复刻的是个浏览器"这句话的边界其实很窄。

**最容易搞错的一点**：本地校验（Python）**从来没实现 webView 语义**——URL 选项里的
`webView` 被解析出来后**静默忽略**，一律当普通 HTTP 请求。于是：

- 那些 5★ 的 webView 源，**恰恰是"忽略该选项后仍然跑得通"的证明**（站点对普通客户端
  本来就返回可用 HTML）；
- 而 JVM 服务跑的是 App 真代码，它会**忠实地**去开 WebView → **反而比现在的本地校验更差**。

→ 所以「剥掉该选项」不是优化，是**必需的补偿**：不做的话，服务上线第一天就会在这批
源上集体退步。

**同源策略挡住的那条近路**：让"网页前端那个浏览器"替我们渲染——不行。跨域 `fetch`
读不到响应体；跨域 `<iframe>` **会渲染、JS 也会执行，但 `contentDocument` 读不到**。
渲染发生了，结果取不回来。这是安全边界，不是工程问题。唯一绕法是浏览器扩展（要用户
安装 + 按浏览器维护），门槛比"起一个 headless 浏览器"高。

**结论**：缺口只有一处（浏览器），补法三条——**剥选项**（0 成本）、**复用本机
Edge/Chrome 走 CDP**（几百行，不用额外下载浏览器）、**真机兜底**。别为它改 App 源码。

### 四十九点五、浏览器桥（CDP）落地时踩的四个坑（2026-09-19）

**定位**：`BackstageWebView` 只替换**取数**那一步，而 App 的解析层都收
`body: String?`（`BookList.analyzeBookList` / `BookContent.analyzeContent`）——
所以**不需要 shadow WebView**：自己拿渲染后的 HTML，喂给同一套解析器即可。
四个坑都是"进程与本机资源"层面的，与协议无关：

| 坑 | 症状 | 根因与修法 |
|---|---|---|
| **子进程输出没人读** | 手工跑（重定向到 /dev/null）一切正常；JVM 里启动却报「调试端口没起来」，进程还活着 | `redirectErrorStream(true)` 只是把 stderr 并进 stdout，**管道缓冲写满后子进程阻塞在写日志上**。必须起个线程把输出读掉（顺便留最后 40 行，失败时贴进原因里） |
| **profile 单例** | 之前所有启动都报「浏览器进程已退出」，且子进程毫无输出 | 同 `--user-data-dir` 的 **Edge/Chrome 是单例**：已有实例时新进程把请求转交过去然后自己退出。修法：启动失败时**换一个本次专属 profile 再试一次**（别让整批源卡在"浏览器不可用"上）；排查时先看有没有残留进程占着 profile |
| **一个 OkHttp 客户端两用** | 整批源卡死，jstack 显示 `BrowserBridge.httpGet → launch` | WebSocket 不能有读超时（`readTimeout(0)`＝无限），而 CDP 的 HTTP 端点**必须**有超时；两者共用客户端 = 端点一挂就永久阻塞，而启动路径正持有锁 → 全批陪葬。**拆成两个客户端** |
| **`/json/new` 偶发拿不到页签** | 报 `cdp_error: /json/new 没返回页签` | 改用**启动时就有的那个 about:blank 页签**（`/json/list` 取第一个 `type=="page"`）：少一个端点、少一类竞态；代价是只有一个页签 → 渲染要**串行**（加锁），对"只对空壳源复验"的量级完全够 |

**判据**：这类"本机资源"的坑，**手工命令行能跑通、放到进程里就不行**是共同形状——
先怀疑三件事：子进程的输出谁在读、单例资源被谁占着、超时设置是不是被另一用途污染了。

## 五十、用带缺口的工具去量缺口，量不到

**症状**：面对一个能力缺口（如"JVM 跑不了 WebView"），自然的做法是先统计"有多少源
会受影响"，再据此决定做不做。**这个顺序是错的**。

**根因**：缺口里的源在报告里**混进"失效"**——它们显示为"规则跑不出结果"，不会被单独
数出来。于是「还剩多少条真需要这个能力」这个数，**只有具备该能力之后才测得出来**。
用带缺口的工具量缺口，量到的永远只是「没被挡住的那部分」。

**更贵的一层：缺口会自我固化**。进不了验证的源只有两条路，**都没有自愈机制**：

- 判 **fail** → 用户可能把**能用**的源删掉（正是 §四十四 那条「把工具的欠缺说成源的
  问题」，但它在这里是**持续**发生的）；
- 判 **unknown** → 永远挂在「待验证」，无法收敛。

而库是**持续导入**的（社区源越来越常带 webView 过反爬），这类源只会累积。

**做法（判据要分开）**：

- **检测与标注**：与数量无关、立即做。保证「跑不了」被标成 `unknown` 而不是 `fail`
  ——**不冤枉是底线，不管有几条**。
- **能力本身**：按「这个缺口会不会长期污染结论 + 补它的成本是否已降到有限」决定，
  **不按今天的命中条数**。

**易混点**：这与 §三十一「数字必须带环境，快照不能跨环境比较」是两件事。那条讲
**横向**（快照不能跨环境比）；这条讲**纵向**——快照不能用来决定「要不要具备一个能力」，
因为**能力缺口的规模，快照本身测不出**。

## 五十一、App 接口：先查能力清单，再接（实测数据与对账口径）


**原则**：在本地实现任何规则语义之前，**先查 App 已经开了什么接口**——App 里
Rhino + JSoup + 完整规则引擎本来就在，我们的复刻永远追不上它。

**能力清单**（`web/KtorServer.kt`，远多于我们原先用的两个）：

    HTTP 1122   /saveBookSource  /saveBookSources(吃 JSON 数组)  /deleteBookSource(s)
                /getBookSource   /getBookSources   /refreshToc
                /getChapterList  /getBookContent   /getBookshelf
    WS   1123   /bookSourceDebug(我们用)  /rssSourceDebug  /searchBook

- **`/searchBook`**：`{"key": "<关键词>"}` → 按 App 的 `SEARCH_SCOPE`（空串 = 全部启用源）
  并发搜，流式推回 `SearchBook{bookUrl, origin(＝书源 URL), originName, name, ...}`。
- **`getChapterList` / `getBookContent` 是书架维度**（`BookController.kt` 明写
  「未在数据库找到对应书籍，请先添加」）——**不能用它校验书源**，那是用户的阅读数据。
  但注意：**`WebBook.getChapterListAwait` 那一层是免书架的**（直接吃 BookSource 对象），
  书架限制只在那层 HTTP。

**读源码的教训**：第一遍只读了「我们用到的那两个端点」附近，于是漏掉批量接口，还按
「单数端点 × N」估出「推 3774 条要几小时」。**读源码要读完整的能力清单，不是只读自己
用到的那一段**——那正是把既有能力漏掉的方式。

**实测数据形状（3774 条在用源，一次真实设备运行）**：

- **每词一次搜索 ≈52 秒**，3000+ 条与 50 条同量级（App 内部全并行，**规模不敏感**）；
  无主动断连（收到的 close 是正常收尾）。**一条连接只服务一个关键词**，多词要重连。
- **命中的是「行」，不是「源」**：大众词一次返回 **1872 行**，去重后只来自 **77 个来源**
  （单源平均 24 本）。**判定要按 `origin` 去重数源，不能数行**。
- **`origin` 是原文，但库里的原文本身脏**：直配率 93.5%–98%，失败样例是**前导空格**
  与**尾斜杠**；`strip()` + 去尾斜杠后 **77/77 全对上**。→ 对账两侧都要宽松归一（§五 的
  同一件事，这次知道脏在哪）。
- `respondTime` 恒 `-1`（搜索事件不带单源耗时）；`type` 恒 `64`（内部位掩码，**不是**
  `bookSourceType`，别拿它判类型）。
- **App 原有源会一起被搜**：搜索范围是「App 当前库全部启用源」，不是「你刚推的那批」
  → **不能假设流里的都是自己推的**，对账按 `origin` 集合运算。

**备份 / 还原的判据（推翻过一次，记下来）**：一开始以为「库就是从 App 导出的 →
设备稳态 = 库 → 不必备份还原」，**这是想当然**：导出之后两边各自演化。
`saveBookSources` 是 `@Insert(REPLACE)`、按 `bookSourceUrl` 精确匹配，所以：
App 有库没有 → 不碍事；库有 App 没有 → 推上去就是（插入）；**唯一的真损失是「同 URL
两边版本不同」——推送会覆盖掉 App 侧的修改，还原是唯一能拿回的机制**。
结论：设备兼职日常使用就保留备份还原（成本 2 个请求、几秒钟），确认是纯测试机才可省。

## 五十二、状态词表一改，存量字符串就成了「别人家的词」

**背景**：2026-09 把健康档位从 9 档收成 6 档（ok / auth / gfw / cert / pending / dead），
判据是**下一步动作是否相同**——删 / 修 / 重测 / 翻墙 / 连 App 试。timeout、error、
no_search、skipped 四种失败看起来各不相同，但动作是同一个（重跑一次校验），并进
pending；反过来 AUTH 与 PENDING 名字只差一个字，动作却完全不同（连 App 试 vs
重跑），必须分开。**判据是动作，不是语义相近、更不是名字像不像。**

### 一、「未校验」不是一档状态，是数据缺失

它没有 checks 行，是**我们没跑过**，不是**源怎么样**。把它升成枚举里的第 N 档，
等于把自己工具的欠缺升格成关于源的结论（§五十 的同一件事）。正确位置是**派生筛选**：
统计条上一个灰 chip、筛选取值 health=none（`health IS NULL`）。

顺带记住**加一档的成本是 O(所有派生表)**：状态标签表、分组映射表、排序表、统计条、
两个下拉、分布表、位串——少一处就是「那种源在统计条上一个都数不到」。

### 二、否定式命名：别把「不知道」说成结论

这一档最终叫「待验证」，中间差点叫「异常」。**「异常」是肯定断言**：那会把 711 条
超时 + 300 多条**一次请求都没发过**的新源一起标成坏的。同类纪律在本仓已有两处先例
（`organizer.infer_health_from_group` 的兜底不能是 AUTH；回放器把「做不到」判
unknown 而不是 fail）——**兜底档的名字必须是否定式的、非断言的**。

### 三、改词要清的是存量，不只是代码（本次最值钱的发现）

`sources.group_name` 里存的是**当时写下的那个词**。词表一改，存量字符串就变成前端
认不出的东西——而前端认不出时**不是「原样显示」，是降级成用户标签**：可编辑、可导出，
出现在标签列里（`core/tags.py` 判定表注释早就预警过这个坑）。实测：1051 条「需验证」
+ 98 条「需代理复检」。

所以**改词必须配一次存量换词迁移**，映射表放在 `core/tags.py`
（`RETIRED_STATUS_TAG_RENAMES`），与旧分组回读共用一份。

### 四、换词 ≠ 重算（这条是被测试逼出来的）

迁移第一版顺手调了 `rebuild_system_tags()` 重建组名，测试立刻红在
`test_migration_from_legacy_schema` 上。原因：**重算按 checks 表推导，而「从未校验」
的源没有 checks 行**，重算会把它们统一压成「待验证」——**抹掉导入时从旧分组推断出来的
状态**（`infer_health_from_group` 存在的意义就是留住那个信号，见 WORKFLOW「未联网时
状态只从旧分组迁移」）。

判据很朴素：**这一步的任务是「换名」还是「重算」？名字里已经写着。** 换名只换词、
保留每个源自己的状态；锁定行也照改（用户钉住的是**状态**，不是**这个词怎么写**），
而 `rebuild_system_tags` 必须跳过锁定行——两者在这点上正好相反。

### 五、变异验证本身也会选错变异点

本轮 9 个变异第一轮有 2 个「绿」，一查**都是变异点选得不对**，不是测试没守住：
删掉了集合里的冗余项（近乎等价）、`assertLess(a, b)` 却把 a 调得更大。
**变异变绿，先自问「这个变异真的会改变行为吗」，再去改测试。**

另有一个工具坑：**`Path.write_text` 在 Windows 上把 `

「改坏 → 跑测试 → 还原」会把整个文件的行尾换掉（git 归一后 diff 干净，所以看不出来，
但工作区已经不一致了）。变异脚本的还原要走**二进制读写**。

## 五十三、S1 全量实测：结论分布、归因口径与「环境缺口清零」的判据

**背景**：JVM 校验服务（§四十八/§四十八点五）全量跑完 3774 条在用源（2026-09-19，
17 分钟，8 并发 + 3g 堆）。这份实测数据是后续一切「该信谁」判断的基线，也沉淀了
两条方法论。

**结论分布**（meta `jvm_check:<batch>:<url>`）：

| 结论 | 数 | 归因细分 |
|---|---|---|
| ok | 1324 | —— |
| no_result | 935 | 请求成功但搜索无结果（留给多词复核） |
| error | 1444 | 连接重置（被墙特征）462 / JS 规则失败 313 / DNS 死亡 291 / JSONPath 不符 152 / 超时 66 / 其他 220 |
| timeout | 61 | 每源 25s 硬超时 |
| empty_js_shell | 10 | 剥 webView 后页面是 JS 壳（§四十九 的 unknown 语义，不冤枉） |

**两条方法论**：

**① 「环境缺口清零」要靠 root cause 链证明，不是靠「没报错」**。批量跑完后逐类
抽 error 看 `root`/`root_stack`（§四十八点五 的机制），确认每个失败都能归到
「源的问题 / 网络的问题」，没有一条是「Robolectric 环境缺了什么」——**环境缺口
清零是验证出来的结论，不是跑完没崩就算**。中途 OOM 一次（约 600 条崩）：测试 JVM
默认堆不够 Robolectric 加载整个 App，init 脚本 `maxHeapSize = 3g` 后全程稳。

**② 断点续跑靠「逐行独立 + URL 去重合并」**：NDJSON 每行是独立 JSON，崩了之后
已写出的行完整可复用；剩余批次按「未出现在已完成集合」切出，两批合并按归一化 URL
去重（§五 的归一口径）。**别把中间状态写进单一 JSON 数组**——崩在中间整份作废。

**剥 webView 的直接收益（实测）**：147 条带 webView 标记的源剥掉后 16 条直接 ok
——「作者觉得需要」≠「规则需要」的实证；9 条归 empty_js_shell 待浏览器桥（S3-4）。

### 补：**同一 IP 连续两轮全量会互相污染**（2026-09-19 实测）

改完判定口径要付一次全量重跑，很自然会「先 depth=3 跑一遍、再 depth=4 跑一遍」。
实测代价：第二轮把一批源打成 `pending`（域名/搜索段就失败），
`pending` 1211 条里 **1049 条 depth=1**——它们不是"源坏了"，是被限流了。
两轮之间的分布差异因此**不能当作口径变化来读**。

做法：**一轮跑到目标深度**（要正文结论就直接 depth=4，别先 3 后 4）；
要比较两轮结果时，先按 `probe_depth` 分层看，把 depth=1/2 的那批单独归因，
否则会把限流算成结论变化。

## 五十四、链路越深，结论越要带 stage：同一段代码里「哪一步坏了」必须可分

**背景**：S3 把 JVM 校验从搜索档扩到目录/正文段。搜索档的六态结论（§五十三）在
多段链路下不够用——「no_result」是搜索没结果还是目录没章节？「error」是搜索页
打不开还是正文页打不开？

**规矩**：多段链路的结论要带 **`stage` 字段**（结论挂在哪一段），段内失败不新造
状态、沿用同一套六态。判据是**归因报告和界面 tooltip 都要能回答「搜索坏了还是
正文坏了」**——回答不了的话，用户面对「JVM✗」不知道该修哪段规则。

**链路形态照抄 App 自己的调试链**（`Debug.kt` 的
`searchDebug → infoDebug → tocDebug → contentDebug`），不要发明顺序：
book 由搜索第一条结果来、`book.tocUrl` 由详情段填（空则回退 bookUrl）、
正文段的 `nextChapterUrl` 取目录第二条。**`needSave=false` 是硬约束**——
校验器对 App 的数据库/缓存目录必须是只读的，任何一段落盘都破坏零入侵边界。

**每源总预算**：目录+正文比搜索慢 2-4 倍，`timeout` 是**每源**总预算（多段共享），
不是每段各给一份——否则一个慢源能把整场拖成 O(源数 × 段数 × timeout)。

### S3-2 实测：三种「结论形状对、意思错」的形态（2026-09-19）

正文段跑完 100 条，三种问题都不是崩溃，而是**结论看起来正常**：

| 形态 | 症状 | 判据 |
|---|---|---|
| **引擎把异常当值返回** | `java.ajax` 拿到非 URL 抛 `IllegalArgumentException`，Rhino 把**异常消息字符串**当 JS 结果返回 → 「非空即通过」判它 ok，那段"正文"是一行报错（实测塔读系 4 条，占当批 ok 的 5%） | **「非空即通过」的前提是「非空的是内容」**——引擎吞异常时前提不成立。判据锚在异常的**形态**上（全限定类名/JS 报错形态/okhttp 的 URL 校验消息），不是"含 Exception 字样"：误伤真源比漏掉假通过更贵 |
| **源级空 ≠ 网络错误** | App 自己抛 `ContentEmptyException`（`BookContent.kt`）/ `TocEmptyException` → 被归进 `error`，与连接重置、DNS 死亡混成一桶 | 异常名里带 `EmptyException` 的是**关于源的结论**（规则跑不出内容），落 `no_result`；归 `error` 会让归因报告把它算进网络问题，而两者的下一步动作不同 |
| **超时文案谎报来源** | 14 条报「每源总预算 60s 用尽」，而记录里的耗时只有 ~400ms——**耗时根本没记**，文案是拿参数硬写的 | 两种超时要分开说：预算用尽（我们的参数）vs 源慢/App 内部超时。**实测 timeout=90 时它们仍在 60–65s 断**，源头是 App 的 okhttp `.readTimeout(60, SECONDS)`（`HttpHelper`）→ **每源总预算要 > 60s 才有区分度**。另有一般教训：**异常分支也要记耗时**，否则文案只能靠猜 |

## 五十五、同源不同判还有两块没补的：类型判定与正文后处理字段

**背景**：本地回放对 `bookSourceType` 与正文后处理字段的处理能力，与 App 有结构性
差距。两块都做过调研、都核过源码与全库数据——**证据在这里，动作在 TODO §七**。

**一、类型判定（`core/reclassify.py` 的 `infer_type_static`）**：

- `bookSourceType` 决定的是**阅读器走哪条渲染路径**（`BookSourceType.kt` 的
  `@IntDef`），而现有判据全是「域名/名称像什么」——**用内容线索猜渲染路径**。
- 数学上判不出 1（音频）和 3（下载源）：出口只有 `2`/`0`/`-1`；已声明的 1/3 被无视；
  `-1`（证据不足）的语义是「保持原样」，而多数源本来就是默认 `0` →
  **「保持原样」就是保持错误**。
- **被审对象给自己投票**：`declared == 2 → manga +1`、`declared == 0 → novel +1`
  ——声明的类型正是要被推翻的结论，却参与计分。权重低、方向上多数时候无害，
  但与 AGENTS #11「判定输入不能是我们自己写进去的结论」有张力。换判据时应顺手拿掉。
- **真正的解法**是对齐 `Debug.kt:329-332`：用 `book.isWebFile`（由 `downloadUrls`
  存在决定，`BookExtensions.kt:94`）判下载源，**不是猜的**。但实测管理库 3861 条里
  **带 `downloadUrls` 的是 0 条**——思路现在搬不过来。**没有信号就加出口，只会把
  「猜域名」换成「猜别的东西」**；先调研库里存在哪些能定案的结构信号，再谈判据换不换。

**二、正文后处理字段（App 用、我们一条都不用）**——比 webView 更直接的「同源不同判」：

| 字段 | App 在哪用 | 非空（3861 条，2026-09-16） |
|---|---|---|
| `replaceRegex` | `BookContent.kt:190` 正文替换（走**规则引擎**不是裸正则） | **1024 条（26.5%）** |
| `title` | 正文内取标题 | 41 |
| `sourceRegex` | WebView 分支页面源码正则 | 19 |
| `payAction` / `imageDecode` / `callBackJs` | 漫画购买 / 图片二次解密 / 事件回调 | 13 / 11 / 1 |
| `subContent` | 副文规则 | **0** |
| `nextContentUrl` | 下一页 | **已建模**（唯一对齐的） |

**风险评估**：`replaceRegex` 覆盖面大但**风险方向单一**——我们判「非空即通过」，

**共同判据**：调研先行——「App 在用什么」逐个核源码，「库里有多少」拿管理库实测，
两个数都有了才决定做不做。别凭字段名想当然（`ruleContent.image` 的教训，§十九）。

## 五十六、JVM 调试通道的可行性：证据都在 App 侧，缺的只是工程（2026-09-19 调研）

**结论**：单源调试不需要真机——`Debug` 管线在 JVM 里可直接跑，事件流可直接订阅；
真机收窄为「登录态的源头 + 终验收」。**动作在 TODO §一点八**，这里放接口证据。

**一、事件流是公开 Flow，不需要 WS**。`Debug.startDebug(scope, bookSource, key):
Session`（Debug.kt:236）按 key 前缀分派：纯关键词=搜索、绝对 URL=详情、`::`=发现、
`++`=目录、`--`=正文。`Session.events`（Debug.kt:400-421）是
`Channel(UNLIMITED).receiveAsFlow()`，Error/Completed 事件会自动关流并清
`activeSession`。设备 WS（BookSourceDebugWebSocket.kt:40）也只是 collect 这个 Flow
的又一个消费者——**它没有任何 JVM 拿不到的独占信息**。
两个坑记好：① `Debug.log` 只在 `debugSource == sourceUrl` 时 emit（Debug.kt:54），
一次只能有一个活动会话，并发调试必须串行或分进程；② `Debug` 是单例 object，
Robolectric 进程里跑完一次要重置状态。

**二、`BackstageWebView` 干两步，不是一步**——这是与 S3-4 校验桥的本质差异：
① 加载页面（`loadUrl` / `loadDataWithBaseURL`，BackstageWebView.kt:100-129）；
② `EvalJsRunnable` 在渲染结果上执行**源的 `js` 选项**（无则默认
`document.documentElement.outerHTML`，:369），**结果非空才收**，1 秒重试至 30 次
（:224-247）。S3-4 的校验桥「渲染一次拿 outerHTML」对齐的是默认 js；调试通道要
shadow `getStrResponse()` 就必须把两步都做全，否则带 `js` 选项的源调试结果是错的
——**fixture/桩编码了不完整语义，测试通过≠语义正确**（§二十三的坑，第四次）。
调用点三处：AnalyzeUrl.kt:453/464（POST 分支会先拿 HTTP 响应再在 `html` 上跑 js）、
AnalyzeRule.kt:176、JsExtensions.kt:236/275/321。`sourceRegex` 非空时走
SnifferWebClient（网络嗅探语义），首版 shadow 不做，显式报不支持。

**三、登录/代理源的可调试性分层**（2026-09-19 核源码定）：

- **代理：完全支持**。proxy 是书源 URL 选项里的键（AnalyzeUrl.kt:136-138 解析 →
  `getProxyClient`，HttpHelper.kt:196：HTTP/SOCKS4/SOCKS5 + 账号密码），
  **跟着源走，不是设备环境**。分界只是网络位置——电脑到代理通不通，
  与通道无关。
- **登录态三层**：静态凭证（`loginHeader`，BaseSource.kt:137）是源字段，直通；
  动态 cookie 存设备 `CacheManager`（CookieStore.kt:25），JVM 天然没有，但
  cookie 就是一串字符串，注入一次即可（TODO A3 走 `CookieStore.setCookie`）；
  **只有「登录过程本身」（验证码/短信/风控）JVM 复现不了**——缺的是「取得」，
  不是「使用」。
- 顺带：`BackstageWebView` 每次加载会把 WebView cookie 回存
  `CookieStore.setCookie(tag, …)`（:161-169），shadow 版要注意这一环别断——
  调试中拿到的 Set-Cookie 对后续请求是否生效，取决于这条链路。

**四、为什么值得做**：设备 WS 的 `matched_html` **恒为空串**
（`core/app_debug.py:515`，App 只推文本）——这是设备调试的结构性天花板；JVM 通道
手里握着完整 HTML，`matched_html` 回填后信息量直接超过设备。加上免 IP/预检/推送，
「连 App 调试」在建好后没有残留优势。

## 五十七、「摘」进主干的分支：内容在了，提交不在（2026-09-19）

**症状**：调试与文案两支是**手工「摘」进主干**的（`cherry-pick` + 落主干时适配），
落地后那两个分支还留在仓库里。用 `git merge-base --is-ancestor <提交> master` 一验，
**三个提交一个都不是 master 的祖先**——内容进去了，对象没有。

**根因**：这不是「合并方式的选择」，是一个**状态不一致**：内容在主干、提交在分支，
两边是两套对象。平时它无害——git 的 3-way merge 对「同样的改动各在一边」会自动合
一次（不会重复），所以最容易误判「留着也没事」。

**真正的代价只出现在被适配过的那部分**：文案分支落主干时，把一个必须逐字保留的串
改回原样、又按主干现状重扫了机检基线（-2/+1）；而分支里那份还是旧基线。
**此时再 merge 那个分支，冲突怎么解就把适配顶回去**——而基线是生成物，顶回去
等于静默改了闸门口径，界面上/测试里都看不出来。

**做法**：

- 内容落进主干后**立刻删分支**（`git branch -D`）。要备查的是提交信息与 lessons，
  不是那个分支。
- 「内容真的在主干吗」用 `git branch --contains` / `merge-base --is-ancestor` **验**，
  别凭记忆——本次就是这么发现两支都没进历史的。
- 落主干时若做了适配，**适配就是主干的事实**，分支里那份作废。

→ 已提炼为 AGENTS #19（摘进主干的分支要删掉）

## 五十八、两条「把我们的问题说成源的问题」的静默错（2026-09-19，修口袋漫画时暴露）

修 `口袋漫画`（`www.koudaimh.com`）时同时踩出两条：**都不是「少验一点」，
是结论说反**。两条的共同点是**判据的来源被认错了**——一条把「App 才懂的
URL 选项」当成了地址的一部分，一条把「属性名」当成了标签名。

### 一、URL 选项没剥 → 我们把地址拼错，归因写成「源坏了」

**症状**：修好的源在真机（App 引擎）上四段全通，本地 `check --probe-depth 4`
却写 `content_fail_reason = 正文请求失败(status=404)`。

**根因**：`_probe_content` 拿到规则产出的章节地址后直接 `_abs_url` 就发请求，
而那个地址尾部挂着 Legado 的 `,{"webView":true}`。选项里装的是 **App 才懂的
东西**（`webView` / `method` / `body`），是给 `AnalyzeUrl` 解析的，**不是地址**。
实测对照（同一次请求、同一个站点）：

    .../1.html                         → 200
    .../1.html,{"webView":true}        → 404

于是校验器把「我们拼错了地址」写成「正文请求失败(status=404)」——读起来像
源坏了（AGENTS #4 的同一类错）。改前的记录里 46 条源的 `bookUrl`、60 条
`tocUrl`、64 条 `chapterUrl` 带选项，都在同一条链上。

**做法**：`core.urls.rule_url(base, raw)` = 先 `split_url_options` 再 `abs_url`，
`checker`（详情/正文）、`toc_page`（tocUrl 的规则分支）、`verify`（bookUrl/章节）
四处统一走它。**与 `core/app_debug.py` 里那条「保留选项尾巴」的用法不冲突**：
那边要把 URL 连同选项当**身份**存起来（`absolute + tail`），这里只要一个能发的
地址——两件事，别互相套用。

**留下的诚实结论**：同一个源改完后再跑，正文段变成
`content_ok=None` + 「JS 规则需要 Legado 的 Rhino 引擎，无法离线回放」。
**这才是对的说法**——「我们验不了」和「源坏了」是两件事。

### 二、`title` / `style` / `label` 被当标签 → 取值规则静默取空

**症状**：`class.a@title` 恒返回空，而 App 用同一条规则取得到书名。

**根因**：这三个词**同时**在 `COMMON_ATTRS` 与 `HTML_TAGS` 里，而回放器的
`_is_selector_like` 先判 HTML_TAGS，于是 `class.a@title` 被解成
「在 `a` 里再选一个 `title` 元素」→ 永远匹配不到。

**依据是 Legado 的语义，且要说准是哪一半**：取值规则走
`getResultList` → 末段交给 `getResultLast`，那里除
`text`/`textNodes`/`ownText`/`html`/`all` 五个动作外**一律** `element.attr(末段)`
（`AnalyzeByJSoup.kt` 的 `getResultLast`）。所以末段是**属性名**，不是选择器。
实测末段为 `title` 的取值规则约 **170 条**（`ruleToc.chapterName: "@title"` 这种
「取当前节点的 title 属性」的惯用写法就在其中），改前全被静默算成「取不到」。

**别改宽**：**列表**规则不走这条路——`getElements` 把每个 `@` 段都当选择器，
`class.chapter-list@tag.a` 必须仍能跑出章节。所以修复只落在
「末段 + 单段」两个位置（`_is_attr_or_action_name`），实测列表字段
（bookList/chapterList）末段用这三个词的规则 **0 条**，碰不到。

### 三、顺带修掉的工具坑：`tools/apply_edits.py` 会把整文件转成 CRLF

它用 `read_text`/`write_text` 往返，而 Windows 上 `write_text` 把 `\n` 全翻成
`\r\n`——本仓库源码是 LF，于是**改一个字就整文件换行尾**，且 diff 看不出来
（两边都归一化）。已改成按文件自身行尾读回写回（读时先归一成 LF 再匹配锚点，
写时还原）。这条本来就在 `agent-write-safety` §三的表里，只是那个「可复用的
应用器」自己没遵守。

### 四、站点侧的事实（不是我们的问题，但要知道）

`口袋漫画` 的图片走 `params` 加密 + `xhr_mode`：章节页里
`var params = '<base64>'`，由 `cms.min.js`（jsjiami 混淆）用 **AES-CBC** 解出
`{chapter_images, images_hosts, images_base64, xhr_mode, ...}`；`xhr_mode=true`
时页面用 XHR 拉图再挂 blob，**DOM 里根本没有图片地址**——所以
「渲染后读 `img.src`」这条路是死的，必须读解密后的 `params`。

**另一个必须知道的事实**：它的图片是**带签名的 CDN 直链**（`x-expires` /
`x-signature`），**老章节的签名已经过期**（实测 `海贼王` 第1话 8/8 张 403，
而它的最新话 8/8 张 200）。所以"这本漫画打不开"未必是源的错——先看是不是
只剩老章节。浏览器里同样打不开（页面自己会显示「加载失败，无效图片」），
**不是我们抓不到，是站点确实没有**。

→ 已提炼为 AGENTS #20（规则产出的 URL 要剥选项）、#21（取值规则末段是属性名）
